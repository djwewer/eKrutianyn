_Перевірено 2026-10-29: `ai-assistant.service.ts` досі не використовує дані гуртка/виховника._

**Опис:** зараз системний промпт AI-виховника (`buildSystemPrompt` у
`apps/api/src/ai-assistant/ai-assistant.service.ts`) будує контекст лише

## 🟢 Picker не реєструє доступ до вибраного файлу (`drive.file`) — "File not found" після вибору

**Опис:** звʼязковий підключав Книгу судді через Google Picker (`/suddivstvo`)
— файл реальний, обраний саме через Picker, доступний йому в Drive — але
бекенд одразу падав з `File not found: <fileId>` при першому ж читанні

не викликав `PickerBuilder.setAppId(...)`. Для `drive.file`-скоупу цей
виклик обовʼязковий — без нього Picker візуально дає вибрати файл (callback
спрацьовує), але фактичний грант доступу для OAuth-токена на цей конкретний
файл не реєструється, і будь-який наступний виклик Drive API повертає 404.

**Що зроблено:** `apps/web/lib/google-picker.ts` (комміт `ec911d2`) — обидва
picker-и (`openGoogleDriveFolderPicker`, `openGoogleSheetPicker`) тепер
викликають `.setAppId(NEXT_PUBLIC_GOOGLE_PROJECT_NUMBER)`. Андрій задав
`NEXT_PUBLIC_GOOGLE_PROJECT_NUMBER` у Vercel і перепідключив таблицю —
підтверджено живим тестом: Книга судді читається (2026-09-30).

## 🟢 Одна роль в курені на юнака

**Опис:** юнака можна було одночасно призначити на кілька позицій — і на
рівні куреня (курінний + суддя + писар одночасно), і на рівні гуртка
(наприклад, ройовий + заступник ройового того самого гуртка одночасно).
Тепер: юнак може займати лише одну активну позицію в межах одного scope
(KURIN або HURTOK) одночасно — але може одночасно мати одну KURIN-позицію
і одну HURTOK-позицію. Призначення нової позиції автоматично знімає
(`removedAt`) будь-яку іншу активну позицію юнака в тому самому scope
(авто-заміна, не помилка) — узгоджено з Андрієм 2026-09-12.

**Що зроблено:** `apps/api/src/kurin-positions/kurin-positions.service.ts`,
метод `assign()` — фільтр знімання (`updateMany`) розширено з "той самий
слот" до "той самий слот АБО той самий userId" в межах scope. Комміт
`7fb0963`, задеплоєно на бекенд-VPS.

## 🟢 approve()/reject() на запит "Масовий імпорт" — гонка при одночасному рішенні

**Опис:** `reject()` в `ApprovalRequestsService` досі читає статус запиту
й потім оновлює його двома окремими операціями (не однією умовною), на
відміну від `approveBulkImport()`, який тепер атомарно "захоплює" запит
через `updateMany({ where: { status: PENDING } })`. Якщо `approve()` і
`reject()` виконуються одночасно на той самий запит, можливий стан, коли
запит позначений REJECTED, хоча рядки вже застосовані через `approve()`.

**Що зроблено (2026-10-10):** `reject()` тепер атомарно "захоплює" запит через `updateMany({ where: { id, status: PENDING } })` з перевіркою `count`. Той самий умовний claim додано всередині транзакції загального `approve()` (CREATE_JUNAK/CHANGE_*) — якщо паралельний `reject()` виграв, транзакція відкочується разом зі створеним юнаком. Покрито e2e-тестом одночасного approve/reject.

**Де копати:** `apps/api/src/approval-requests/approval-requests.service.ts`,
метод `reject()` — замінити прямий `update` на умовний `updateMany({ where:
{ id, status: PENDING }, data: {...} })` з перевіркою `count === 1`, як уже
зроблено в `approveBulkImport()`.

## 🟢 Масовий імпорт: збій під час обробки рядків залишає запит APPROVED без результатів

**Опис:** `approveBulkImport()` спершу атомарно позначає запит APPROVED, а
тоді обробляє рядки. Якщо сама обробка впаде з винятком поза
`processRow`'s власним try/catch (наприклад, `newData.rows` пошкоджений,
або впаде зʼєднання з БД), запит лишається APPROVED без `results` — і його
вже не можна ні повторно підтвердити, ні відхилити.

**Що зроблено (2026-10-10):** `approveBulkImport()` перевіряє, що `newData.rows` — масив, ДО того як позначити запит APPROVED (інакше 400, запит лишається PENDING і його можна відхилити). Цикл обробки обгорнуто в try/catch: при падінні в `newData` пишуться часткові `results` і `processingError` (безпечний текст без сирої помилки; сира йде лише в лог).

**Де копати:** `apps/api/src/approval-requests/approval-requests.service.ts`,
метод `approveBulkImport()` — обгорнути цикл обробки рядків у try/catch,
що при падінні записує `results` із поясненням помилки замість мовчазного
"APPROVED без даних", або розглянути окремий статус на кшталt
`PROCESSING_FAILED`.

## 🟢 Масовий імпорт: зʼязковий не бачить, ЩО саме затверджує

**Опис:** сторінка запиту (`approval-requests/[id]/page.tsx`) показує
`newData` для `BULK_IMPORT_JUNAKY` як сирий `<pre>{JSON.stringify(...)}</pre>`

цьому вигляді). Це єдина лінія захисту, що лишилась для решти посад/полів,

**Що зроблено (2026-10-10):** `GET /approval-requests/:id` для `BULK_IMPORT_JUNAKY` повертає `matchedJunaky` (мапа `matchedUserId` → поточні дані юнака; лише в межах куреня й ролі JUNAK). Покрито e2e (API + Playwright зі скріншотом).

**Де копати:** `apps/web/app/approval-requests/[id]/page.tsx` — для
`BULK_IMPORT_JUNAKY` рендерити людський список рядків: розвʼязане імʼя
цільового юнака (замість голого `matchedUserId`), що саме зміниться
(email/гурток/посади/дата ступеня) і чи це "новий юнак" чи "оновлення
{ім'я}". Розглянути окрему бекенд-ручку, що розвʼязує `matchedUserId` →
`{firstName, lastName}` пакетом для рендеру.

## 🔴 Масовий імпорт: продуктивність на реалістичних обсягах

**Опис:** і прямий імпорт (`POST .../junak-import/rows`), і підтверджений

## 🔴 Дрібні прогалини майстра імпорту та обробки рядків

**Опис:** зібрані дрібні, не-блокуючі знахідки з фінального рев'ю:

- Пошкоджений `newData.rows` (не масив) у `BULK_IMPORT_JUNAKY` валить
  `approve()` з 500 замість зрозумілої помилки — `create()` не перевіряє
  форму `newData` для цього типу дії.
- Майстер (Крок 3) вимагає лише email; спека також вимагає непорожній
  `lastName` (ПІБ з одного слова має підсвічуватись і блокувати імпорт) —
  зараз такі рядки йдуть з `lastName: ''`.
- `parseUkrainianDate` розуміє лише формат `Д.М.РРРР` — інші локальні
  формати з `values.get` мовчки відкидають дату народження/ступеня без
  попередження користувачу.
- `JunakImportRowResult.error` повертає сирий текст помилки Prisma
  (може містити шляхи на сервері) — і клієнту, і в `newData` затвердженого
  запиту.
- Кілька значень посад в одному рядку на KURIN-скоупі: кожен наступний
  `assign()` знімає попередній — виживає лише останній. Список посад для
  HURTOK-скоупу в майстрі також пропонує KURIN-only типи, що дає
  BadRequest вже ПІСЛЯ створення юнака.
- Нумерація рядків у результатах (`Рядок {r.row + 1}`) рахується після
  фільтрації порожніх рядків, не за номером у самій таблиці.
- Немає Playwright-покриття для курінного/судді шляху майстра (лише
  "не підключено"), і немає regression-тесту саме на блок KURINNYI через
  ЗАТВЕРДЖЕНИЙ (не прямий) імпорт — обидва варто додати.

**Де копати:** здебільшого `apps/api/src/junak-import/`,
`apps/api/src/approval-requests/approval-requests.service.ts`,
`apps/web/app/kurin/junak-import/page.tsx`.

## 🔴 Дрібні знахідки з фінального рев'ю "Оголошень" (2026-10-09)

Непробивні (non-blocking) пункти з фінального рев'ю плану
`docs/superpowers/plans/2026-10-08-announcements.md` — не блокували
мердж, занесено на потім:

- **Публікація блокує відповідь на час відправки push.** `create()` в
  `AnnouncementsService` синхронно чекає на `pushNotifications.sendToKurin`
  перед поверненням. Якщо сама відправка впаде (напр. помилка пошуку
  підписок), клієнт отримає 500 вже ПІСЛЯ того, як оголошення збережене
  в БД — повторна спроба опублікувати створить дублікат. Автор
  оголошення також отримує push на власну публікацію (не виключений із
  розсилки).
- **URL картинки в Tiptap-документі не обмежений.** Писар може вставити
  image-ноду з довільним зовнішнім URL (не лише через `POST
  .../announcements/images`) — браузер кожного читача зробить GET-запит
  на цей хост. Прийнятно для довіреної ролі писаря/звʼязкового, але
  варто мати на увазі.
- **Тест на виключення архівних користувачів з push — лише на мокові.**
  `push-notifications.service.spec.ts`'s новий тест перевіряє лише, що
  `archivedAt: null` передано у фільтр запиту, не що реально збережений
  архівний користувач виключається з реального запиту до БД.
  Integration-тест на реальній `plast_test` дав би сильнішу гарантію.
- **E2E-покриття каскадного видалення — лише для реакцій.** Видалення

## 🔴 Дрібні знахідки з ревʼю аудит-логу (2026-10-27)

Non-blocking пункти з ревʼю окремих задач і фінального ревʼю плану
`docs/superpowers/plans/2026-10-27-audit-log.md` — не блокували мердж:

- **Фільтр за датою: UTC проти локального дня.** `from`/`to` трактуються як
  UTC-дати (`audit.service.ts`), а сторінка групує події за локальним днем,
  тож події між 00:00 і 03:00 за Києвом потрапляють «не в той» день фільтра.
  Також `@IsDateString()` приймає повні datetime, а `to` завжди додає +24 год —
  замінити на валідацію лише дати (`YYYY-MM-DD`) або врахувати часовий пояс.
- **Прогалини в тестах журналу.** Пагінація без рядків з однаковим
  `createdAt` (tie-break по `id` не тестується); період без перевірки
  включного кінця дня (`to`); немає Playwright-покриття фільтрів, пагінації та
  актора «Система»; `describeAuditEvent` без unit-тестів (у `apps/web` немає
  unit-раннера); тест `INVENTORY_ITEM_UPDATED` міняє лише кількість, не назву;
  нічний sync у e2e покриває лише гілку `updated > 0`; немає тесту на
  заміну *іншого* власника тієї ж посади, на події, що їх створює імпорт, і
  на `POSITION_REMOVED` для посади гуртка з `hurtokName`.
- **Текст подій.** `DEGREE_DATE_CHANGED` показує сиру ISO-дату і «на —»,
  коли дату очищено («Очистив дату…»); у запиті на зміну ПІБ записується старе
  імʼя, нового немає; групові кнопки фільтра без `aria-pressed`.
- **`DRIVE_DISCONNECTED`** пишеться, навіть якщо Drive не був підключений
  (шумні записи).
- **`KurinPositionsService.assign`:** попереднє читання позицій, що будуть
  зняті, виконується поза транзакцією (рідкісна гонка = зайвий/пропущений
  `POSITION_REMOVED`) і тягне повний рядок користувача — достатньо
  `firstName`/`lastName`/`nickname`; перенести `findMany` усередину `$transaction`.
- **`updateStartingBalance`:** читання попереднього балансу й оновлення не
  атомарні — два одночасні запити можуть записати застаріле `from`.
- **`InventoryService.create`:** якщо завантаження фото падає посеред
  створення, річ уже існує, але `INVENTORY_ITEM_CREATED` не записано.
- **Гонка в `ARCHIVE_JUNAK` (існувала й раніше):** `archiveUser` виконується
  до «захоплення» запиту (claim), тож паралельне рішення, що програло, лишає
  `USER_ARCHIVED` без `APPROVAL_APPROVED`.
- **Міграція `AuditLog`:** `INNER JOIN` на `User` мовчки пропускає старі рядки
  `ProgressAuditLog`, чий юнак уже не існує (юнаків не видаляють, тож у
  реальності малоймовірно). Перед деплоєм на проді можна порахувати:
  `SELECT count(*) FROM "ProgressAuditLog" p LEFT JOIN "User" u ON u.id=p."junakId" WHERE u.id IS NULL`.
- **Непослідовність `entityId`:** `VYKHOVNYK_*` пишуть id гуртка, а не
  призначення; `KURIN_PROBY_PROGRAM_CHANGED` дублює `kurinId`;
  `DEGREE_DATE_CHANGED` і `TREASURY_STARTING_BALANCE_CHANGED` без `entityId`;
  `DRIVE_DISCONNECTED` пише порожній `details: {}`. Нешкідливо.
- **Адмін-запити в e2e вимагають `ADMIN_USERNAME`/`ADMIN_PASSWORD`** — див.
  наступний пункт про запуск тестів.

**Де копати:** `apps/api/src/audit/`, `apps/web/lib/audit.ts`,
`apps/web/app/audit-log/page.tsx`, `apps/api/test/audit-*.e2e-spec.ts`.

## 🔴 Локальний запуск тестів потребує ручних кроків

**Опис:** на чистому клоні `main` тести не запускаються «з коробки»:
- `npx jest src` у паралельному режимі зависає — працює лише з
  `--runInBand --forceExit`;
- e2e (`npm run test:e2e`) падає з *JavaScript heap out of memory* на дефолтних
  2 ГБ (ts-jest компілює великий `AppModule`) — потрібен
  `NODE_OPTIONS=--max-old-space-size=8192`;
- e2e вимагає в оточенні `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` (Web Push) та
  `ADMIN_USERNAME`/`ADMIN_PASSWORD` — вони є в `.env.example`, але старі
  локальні `.env` їх не мають, і падіння виглядають як
  `No key set vapidDetails.publicKey` та масові `401` у `admin-*` наборах;
- після кожного `git pull` з новими міграціями тестову БД `plast_test` треба
  накочувати окремо: `DATABASE_URL="$DATABASE_URL_TEST" npx prisma migrate deploy`
  (інакше e2e падають на «table does not exist»).

**Де копати:** `apps/api/package.json` (`test`, `test:e2e`),
`apps/api/test/jest-global-setup.ts`, README — додати `NODE_OPTIONS` у скрипт,
fail-fast з поясненням за відсутності VAPID/ADMIN змінних і npm-скрипт
`test:db:migrate`.
