# Автомапінг у майстрі імпорту юнаків — дизайн

**Дата:** 2026-09-30
**Контекст:** `apps/web/app/suddivstvo/junak-import/page.tsx` — майстер імпорту юнаків
з Книги судді (Google Sheets/xlsx). Наразі обидва кроки мапінгу (Крок 1 —
стовпчики → поля юнака; Крок 2 — сирі текстові значення посад → `PositionType`)
вимагають від звʼязкового вручну обирати значення в кожному дропдауні,
навіть коли заголовок/значення очевидні ("Email", "Суддя").

## Мета

Автоматично попередньо заповнювати обидва кроки мапінгу за best-effort
збігом, без нового кроку в майстрі чи додаткового UI — звʼязковий і далі
бачить ті самі дропдауни, просто вже з розумними значеннями за
замовчуванням, які можна виправити вручну. Немає впевненого збігу —
дропдаун лишається "Не імпортувати" (`''`), як і зараз за замовчуванням.

## Не мета

- Не змінює backend, DTO чи схему БД — суто клієнтська UX-зручність над
  даними, які вже є в браузері.
- Не намагається вирішити типографічні варіації/одруківки в значеннях
  посад (див. Крок 2 нижче) — навпаки, свідомо НЕ мапить такі випадки.
- Не додає окремого поля "Ім'я"/"Прізвище" — працює в межах наявного
  списку `JunakImportField`.
- Не чіпає значення, які звʼязковий уже вибрав вручну.

## Архітектура

Нова чиста функція-модуль без React-залежностей:
`apps/web/lib/junak-import-auto-map.ts`, з двома експортами:

```ts
export function autoMapColumns(
  headers: string[],
  savedMapping?: JunakImportColumnMapping[],
): Record<number, JunakImportField | ''>;

export function autoMapPositionValues(
  rawValues: string[],
  savedMapping?: JunakImportPositionValueMapping[],
): Record<string, string>; // rawValue -> PositionType | ''
```

Винесення в окремий модуль (а не інлайн у `page.tsx`) — щоб юніт-тестувати
логіку збігу ізольовано від компонента, без рендеру й без моку React
Query. `page.tsx` лише викликає ці функції один раз, коли зʼявляються
відповідні дані, і використовує результат як ПОЧАТКОВЕ значення стану
(`columnMapping` / `positionValueMapping`) — через `useEffect`, що
спрацьовує, коли дані щойно завантажились і мапінг ще порожній
(`Object.keys(mapping).length === 0`), тож ручні правки користувача
після цього не перезаписуються.

## Крок 1 — мапінг стовпчиків

**Пріоритет для кожного стовпця:**
1. Якщо заголовок цього стовпця точно (рядково) збігається із заголовком
   у раніше збереженому `status.mapping.columnMapping` — береться те саме
   поле, що й минулого разу.
2. Інакше — пошук за ключовими словами (нижче).
3. Інакше — `''` ("Не імпортувати").

**Пошук за ключовими словами:** заголовок нормалізується (`toLowerCase()`,
`trim()`, згортання повторних пробілів). Поля перевіряються в
ФІКСОВАНОМУ порядку від найспецифічніших до найзагальніших — це
запобігає хибним збігам (наприклад, слово "ім'я" в заголовку контакту
опікуна не повинно піти на `FIRST_LAST_NAME`, якщо для контакту вже є
власне, специфічніше правило, перевірене раніше).

Поле матчиться, якщо нормалізований заголовок містить ВСІ підрядки хоча
б з однієї "AND-групи" зі списку нижче:

| Порядок | Поле | AND-групи ключових слів |
|---|---|---|
| 1 | `GUARDIAN_1_EMAIL` | `[1+email]`, `[1+пошта]`, `[батьк+email]`, `[батьк+пошта]` |
| 2 | `GUARDIAN_1_PHONE` | `[1+телефон]`, `[батьк+телефон]` |
| 3 | `GUARDIAN_1_NAME` | `[батьк]`, `[контакт+1]`, `[опікун+1]` |
| 4 | `GUARDIAN_2_EMAIL` | `[2+email]`, `[2+пошта]`, `[мат+email]`, `[мат+пошта]` |
| 5 | `GUARDIAN_2_PHONE` | `[2+телефон]`, `[мат+телефон]` |
| 6 | `GUARDIAN_2_NAME` | `[мат]`, `[контакт+2]`, `[опікун+2]` |
| 7 | `DEGREE_PRYHYLNYK_DATE` | `[прихильник]` |
| 8 | `DEGREE_UCHASNYK_DATE` | `[учасник]` |
| 9 | `DEGREE_ROZVIDUVACH_DATE` | `[розвідувач]` |
| 10 | `HURTOK_POSITION` | `[посада+гурт]`, `[діловодство+гурт]` |
| 11 | `KURIN_POSITION` | `[посада+курен]`, `[посада+курін]`, `[діловодство+курен]` |
| 12 | `EMAIL` | `[email]`, `[пошта]`, `[e-mail]`, `[мейл]` |
| 13 | `PHONE` | `[телефон]`, `[тел.]` |
| 14 | `BIRTH_DATE` | `[дата народж]`, `[днар]` |
| 15 | `NICKNAME` | `[псевдо]`, `[позивний]` |
| 16 | `HURTOK` | `[гурток]` |
| 17 | `FIRST_LAST_NAME` | `[піб]`, `[ім'я]`, `[імя]`, `[прізвище]` |

Стовпці обробляються зліва направо (за індексом). Для кожного стовпця
береться перше поле (за порядком у таблиці), чия хоч одна AND-група
повністю задовольняється — це переможець для цього стовпця. Кожне поле
може бути призначене щонайбільше одному стовпцю за весь прохід: щойно
поле зайняте, наступні стовпці, що теж підпадають під його ключові
слова, його більше не отримують (лишаються `''`, якщо жодне інше поле
теж не підійшло).

**Застереження:** ключові слова для `GUARDIAN_*` — це найслабша частина
списку, оскільки реальне формулювання заголовків для контактів
батьків/опікунів у Книгах судді нам наперед невідоме. Очікується, що
цей список доведеться скоригувати після першого реального тесту з живою
таблицею — це нормально, тому список винесено в один явний масив у
новому модулі, а не розмазано по коду.

## Крок 2 — мапінг значень посад

Інша стратегія, ніж Крок 1: **точний** збіг (не підрядковий), після
нормалізації (`toLowerCase().trim()`), проти статичного словника:

```ts
const POSITION_VALUE_KEYWORDS: Record<string, string> = {
  'суддя': 'SUDDIA',
  'писар': 'PYSAR',
  'скарбник': 'SKARBNYK',
  'інтендант': 'INTENDANT',
  'хорунжий': 'KHORUNZHYI',
  'смм': 'SMM',
  'гуртковий': 'HURTKOVYI',
};
```

(Без `KURINNYI` — ця позиція вже й так виключена зі списку
`POSITION_TYPES` на фронтенді як захищена від імпорту.)

**Чому точний, а не підрядковий збіг:** реальні значення зі скріншота
звʼязкового включали "Заступник Гурткового" і "Скарбника" (родовий
відмінок) — обидва звʼязковий свідомо залишив "Не імпортувати" вручну.
При підрядковому пошуку "гуртковий" є підрядком "Заступник
**Гурткового**"? Ні (відмінкове закінчення відрізняється — "гурткового"
≠ містить "гуртковий" літерально), але "скарбник" **є** підрядком
"скарбник**а**" — це дало б хибний автомапінг заступника на основну
посаду. Точний збіг після нормалізації природно відтворює саме той
вибір, який звʼязковий зробив вручну: канонічні forms мапляться,
відмінкові варіанти й одруківки ("Скарбиник") — ні.

**Пріоритет:** так само, як у Кроці 1 — спершу збережений раніше
`status.mapping.positionValueMapping` для цього точного `rawValue`,
інакше словник вище, інакше `''`.

## Тестування

Юніт-тести на `junak-import-auto-map.ts` (Jest, без React) — покрити:
- прості однозначні заголовки (Email, Телефон, ПІБ, Гурток);
- пріоритет "спочатку збережений мапінг" над ключовими словами;
- порядок пріоритету полів на Кроці 1 (guardian vs generic "ім'я");
- Крок 2: точні збіги проти "Заступник X" і одруківок, які НЕ повинні
  змапитись.

Ручна перевірка в браузері (Playwright не додаю — це не критичний шлях,
і design свідомо best-effort/degradable до ручного вибору).
