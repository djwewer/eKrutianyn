# Аудит-лог («Журнал дій») — дизайн

Дата: 2026-10-27. Піднято з беклогу ("Аудит-лог"), узгоджено з Андрієм.

## Мета

Підзвітність для звʼязковика: бачити, хто, що і коли змінив у курені. Журнал
читається як історія подій, а не як дамп бази.

## Рішення, прийняті в брейнштормінгу

- **Читач:** лише звʼязковий. Інші ролі журнал не бачать і не можуть його змінити.
- **Охоплення:** проба; люди й ролі; гроші й майно; налаштування та інтеграції.
- **Запис:** явні виклики `AuditService.record()` у сервісах (а не Prisma
  extension чи HTTP-інтерсептор) — щоб події були семантичні й читабельні.
- **Наявний `ProgressAuditLog` поглинається** новою таблицею.
- **Збій запису не зупиняє дію.** Помилка `record()` логується в консоль і
  ковтається: блокувати роботу куреня через журнал гірше, ніж втратити один запис.
- **Нічний автосинк у Книгу судді** пишеться одним підсумковим записом від
  «Системи», без рядка на кожного юнака.

## 1. Дані

Нова модель `AuditLog` (замість `ProgressAuditLog`):

| Поле | Опис |
|---|---|
| `id` | uuid |
| `kurinId` | курінь, у якому сталась подія (обовʼязкове) |
| `actorId` | хто діяв; `null` для системних дій (cron) |
| `action` | enum `AuditAction` |
| `subjectUserId` | кого стосується подія (юнак, якому призначено позицію тощо); nullable |
| `entityId` | id основного обʼєкта події (точка, позиція, річ реманенту…); nullable |
| `details` | JSON — знімок читабельних назв і значень (імена, назви точок, було/стало) |
| `createdAt` | час події |

- `details` зберігає назви "як були на момент події", щоб історія не
  ламалась після перейменувань чи видалень.
- Індекси: `(kurinId, createdAt, id)`, `(kurinId, subjectUserId)`, `(kurinId, action)`.
- Журнал append-only: жодних ендпоінтів зміни чи видалення.
- `actor` — relation на `User` без каскадного видалення (користувачів архівують,
  не видаляють).

### Міграція

1. Створити `AuditLog` та enum.
2. Скопіювати рядки `ProgressAuditLog` як `PROBY_POINT_CONFIRMED` /
   `PROBY_POINT_UNCONFIRMED`: `kurinId` — через юнака, `subjectUserId` = `junakId`,
   `entityId` = `pointId`, `details` = `{ pointTitle }` (з `ProbyPoint`, якщо точка ще існує).
3. Видалити `ProgressAuditLog`.
4. Три місця запису (`proby-progress.service.ts` ×2, `kurins.service.ts` ×1)
   переходять на `AuditService`. Читачів старої таблиці в коді немає.
5. `test/utils/clean-db.ts` та тести, що згадують `progressAuditLog`, оновити.

## 2. Запис подій

Глобальний `AuditModule` експортує `AuditService`:

```
record({ kurinId, actorId | null, action, subjectUserId?, entityId?, details? }): Promise<void>
```

Викликається в сервісах після успішної дії (не перед). Усередині — try/catch
з `console.error`/Nest `Logger`.

### Каталог подій

- **Проба:** підтвердження / скасування точки; закриття / перевідкриття проби;
  зміна дати ступеня (у т.ч. Скоб); перенос прогресу при зміні програми куреня.
- **Люди й ролі:** створення / архівація / редагування юнака; призначення /
  зняття позиції (KURIN і HURTOK); зміни гуртків і призначень виховників;
  контакти опікунів (створення, зміна, видалення); рішення (схвалити / відхилити)
  по запитах на затвердження, включно з масовим імпортом.
- **Гроші й майно:** операції Скарбниці (створення, видалення); зміна
  початкового балансу; реманент (додати, змінити, видалити річ, фото).
- **Налаштування та інтеграції:** зміна програми проби куреня; підключення /
  відключення Google Drive; вибір папки; підключення Книги судді, імпорт, ручний
  запис у таблицю; створення АПД; публікація оголошення; нічний автосинк
  (підсумковий запис від «Системи»).

Точний перелік місць виклику фіксується в плані реалізації; нові події
додаються одним рядком у enum і в мапу відображення.

## 3. Читання

`GET /kurins/:kurinId/audit-log` — лише `ZVYAZKOVYI` свого куреня (`kurinId`
шляху має збігатись з токеном, інакше 404).

- Курсорна пагінація за `(createdAt, id)` у спадному порядку; `limit` з розумним
  максимумом.
- Фільтри: група подій (проба / люди / гроші / налаштування), `actorId`,
  `subjectUserId`, `from` / `to`.
- Відповідь: події з `actor` (імʼя, або `null` = «Система»), `subjectUserId`,
  `action`, `details`, `createdAt`.

## 4. Інтерфейс

Сторінка «Журнал дій» (`/audit-log`) у меню звʼязкового. Стрічка по днях,
фільтри (група, людина, період), «Завантажити ще». Текст події будує одна
функція `describeAuditEvent(action, details)` на фронтенді; невідомий `action`
показується нейтрально («Подія: …»), щоб нова подія не ламала сторінку.

## 5. Тести

- Unit: `describeAuditEvent` для кожного `action`.
- e2e: для кожної групи подій — дія створює запис із правильними
  `kurinId`/`actorId`/`action`/`details`.
- e2e: 403 для всіх ролей, крім звʼязкового; ізоляція між куренями;
  пагінація і фільтри.
- Міграція: старі рядки `ProgressAuditLog` переносяться з правильним `kurinId`.
- Збій `record()` не ламає основну дію (мок кидає помилку → дія успішна).
