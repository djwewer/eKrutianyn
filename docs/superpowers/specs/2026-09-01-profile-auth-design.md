# Профіль і базова авторизація — дизайн-документ

## Контекст і межі проєкту

MVP "Ядро + Проби" вже розгорнутий у продакшн (Hostinger VPS + Vercel) і
пройшов перший живий тест зв'язковим. Ключова знахідка: жодна роль не може
самостійно керувати власним акаунтом — немає зміни пароля, зміни email,
відновлення забутого пароля. Для реального використання це не
опціональна фіча, а передумова: без цього кожна забута пара
логін/пароль означає ручне втручання розробника через admin-ключ.

Це перший з семи під-проєктів наступного етапу (перелік — у пам'яті
сесії, `mvp-v1-feedback-backlog.md`). Обраний першим, бо: (1) сам
користувач назвав це найкритичнішим, (2) email-інфраструктура, яку тут
будуємо, знадобиться і сповіщенням (майбутній під-проєкт F) — зробити
один раз, а не двічі.

### Явно поза межами цього підпроєкту

- **Діловоди / посади поверх юнака** (заміна `Role.KURINNYI` на
  призначювану посаду) — окремий, значно більший під-проєкт (B).
  Поточна модель ролей (`Role` — плаский enum, одна роль на юзера)
  лишається без змін.
- **Право зв'язкового підписувати точки проби** — природньо йде в B
  разом з переглядом прав доступу, не сюди.
- **Повний журнал аудиту** (майбутній під-проєкт D) — тут будується
  лише мінімальний `ProfileChangeLog` для одного конкретного випадку
  (самостійна зміна ПІБ/дати народження юнаком чи курінним), не
  універсальна система.
- **Сповіщення як окрема система** (майбутній F) — тут лише
  безпосередньо потрібні листи (відновлення пароля, підтвердження
  email, сповіщення виховнику про зміну ПІБ підопічного). Це не
  повноцінний notification-центр з чергою, шаблонами для всіх подій
  тощо.
- **Власний домен для відправки листів** — свідомо відкладено. Спершу
  через тестовий відправник Resend (`onboarding@resend.dev`), без
  купівлі й прив'язки домену. Перемикання на власний домен — питання
  зміни двох змінних середовища, не архітектури.
- **2FA, сесії з кількох пристроїв, відкликання токенів** — не
  запитувалось, не додаємо.

## Архітектура

Три нові механізми на бекенді (кожен — набір ендпоінтів + за потреби
таблиця), один спільний email-модуль, і відповідні екрани на фронтенді.
Усе — в межах наявної BFF-архітектури (браузер і далі ніколи не звертається
до NestJS напряму, лише через Next.js proxy).

## Дані

Три нові Prisma-моделі. Жодна наявна таблиця не змінюється — лише
додавання, існуючі рядки не займаються.

```prisma
model PasswordResetToken {
  id         String    @id @default(uuid())
  userId     String
  user       User      @relation(fields: [userId], references: [id])
  tokenHash  String    @unique
  expiresAt  DateTime
  usedAt     DateTime?
  createdAt  DateTime  @default(now())
}

model EmailChangeRequest {
  id         String    @id @default(uuid())
  userId     String
  user       User      @relation(fields: [userId], references: [id])
  newEmail   String
  tokenHash  String    @unique
  expiresAt  DateTime
  usedAt     DateTime?
  createdAt  DateTime  @default(now())
}

model ProfileChangeLog {
  id        String   @id @default(uuid())
  userId    String
  user      User     @relation(fields: [userId], references: [id])
  field     String
  oldValue  String?
  newValue  String?
  createdAt DateTime @default(now())
}
```

**Чому зберігається хеш токена, а не сам токен:** той самий принцип, що
й `passwordHash` — якщо базу колись прочитають (бекап, дамп, компрометація),
токени відновлення пароля/зміни email не повинні бути одразу придатні до
використання. Токен генерується випадковим рядком, у листі йде сирий
токен, у базі — його хеш (SHA-256 достатньо, це не пароль, а
одноразовий короткоживучий секрет).

**Чому окрема `ProfileChangeLog`, а не розширення наявного
`ProgressAuditLog`:** той пов'язаний конкретно з підтвердженням точок
проби (`JunakProgress`), інша природа даних. Коли будуватиметься D
(повний аудит), обидві таблиці — природні кандидати для об'єднання чи
заміни єдиною системою; наразі не варто наперед вгадувати її форму.

## Бекенд: нові ендпоінти

Усе під `JwtAuthGuard` (діє на залогіненого користувача, без нового
guard'а).

### `PATCH /users/me`

Тіло: будь-яка підмножина `{ nickname?, phone?, firstName?, lastName?,
birthDate? }`.

- `nickname`, `phone` — оновлюються без обмежень для будь-якої ролі.
- `firstName`, `lastName`, `birthDate` — оновлюються напряму (без
  approval-запиту) для будь-якої ролі. **Якщо роль актора входить у
  `PROBY_TRACKING_ROLES`** (тобто `JUNAK` або `KURINNYI` — той самий
  спільний список з `common/proby-tracking-roles.ts`, що вже визначає
  "юнацькі" ролі в системі), кожна зміна цих трьох полів додатково:
  1. пише рядок у `ProfileChangeLog` (по одному на кожне змінене поле);
  2. якщо в актора є призначений виховник (через `hurtokId` →
     `VykhovnykHurtok`) — надсилає йому лист через `MailService`.
     Якщо виховника не призначено, крок 2 просто пропускається
     (крок 1 — лог — відбувається завжди).

### `PATCH /users/me/password`

Тіло: `{ currentPassword?, newPassword }`.

- Якщо в юзера вже є `passwordHash` — `currentPassword` обов'язковий і
  звіряється (`argon2.verify`) перед зміною.
- Якщо `passwordHash` ще немає (юзер заходив лише через Google) —
  `currentPassword` не потрібен, це встановлення першого пароля.

### `PATCH /users/me/email`

Тіло: `{ newEmail, currentPassword }`. Перевіряє пароль (та сама логіка,
що й вище), перевіряє, що `newEmail` ще ніким не зайнятий, створює
`EmailChangeRequest` і надсилає лист-підтвердження на **нову** адресу.
`User.email` не змінюється, доки лист не підтверджено.

### `GET /auth/confirm-email-change?token=...`

Без авторизації (посилання з листа). Знаходить `EmailChangeRequest` за
хешем токена, перевіряє строк дії й що ще не використаний, оновлює
`User.email`, позначає запит використаним.

### `POST /auth/forgot-password`

Тіло: `{ email }`. Завжди відповідає `200 { ok: true }` незалежно від
того, чи існує такий email — щоб не дати спосіб перевіряти, які email
зареєстровані в системі. Якщо існує — створює `PasswordResetToken`,
шле лист.

### `POST /auth/reset-password`

Тіло: `{ token, newPassword }`. Перевіряє токен, оновлює
`passwordHash`, позначає токен використаним, **інвалідує всі інші
невикористані токени цього юзера** (типова практика — новий пароль
знецінює старі посилання на відновлення).

## Email-інфраструктура

Новий модуль `apps/api/src/mail/` — тонка обгортка над Resend SDK,
`MailService` з методами:

```ts
sendPasswordReset(to: string, resetUrl: string): Promise<void>
sendEmailChangeConfirmation(to: string, confirmUrl: string): Promise<void>
sendProfileChangeNotification(to: string, params: {
  changedUserName: string;
  field: string;
  oldValue: string | null;
  newValue: string | null;
}): Promise<void>
```

Помилка відправки листа **ніколи не провалює основну операцію** — якщо
`sendProfileChangeNotification` впаде (Resend недоступний тощо), зміна
ПІБ/дати народження все одно застосовується і логується, лист просто
не піде (помилка йде в лог сервера). Для `forgot-password` й
`email-change` це критичніше (без листа юзер не зможе завершити дію) —
там помилка Resend повертається як `502`, з зрозумілим повідомленням.

Нові змінні середовища бекенду:
- `RESEND_API_KEY`
- `MAIL_FROM` — початково `onboarding@resend.dev`, пізніше — адреса на
  власному домені.
- `FRONTEND_URL` — базова адреса фронтенду (`https://...vercel.app`),
  потрібна, щоб будувати посилання в листах
  (`${FRONTEND_URL}/reset-password?token=...`).

## Фронтенд

Нові сторінки в `apps/web/app/`:
- `settings/page.tsx` — доступна будь-якій залогіненій ролі (посилання
  в `nav.tsx` для всіх). Дві секції: "Обліковий запис" (email зі
  статусом "очікує підтвердження" під час зміни; пароль), "Особисті
  дані" (нікнейм, телефон, ПІБ, дата народження).
- `forgot-password/page.tsx` — форма email → повідомлення "перевір
  пошту" (та сама відповідь незалежно від результату, як і бекенд).
- `reset-password/page.tsx` (`?token=`) — новий пароль → успіх →
  редірект на `/login`.
- `confirm-email-change/page.tsx` (`?token=`) — підтверджує токен при
  завантаженні, показує результат.

Окремий дрібний фікс у межах цього ж підпроєкту: спільний словник
`lib/role-labels.ts`:

```ts
export const ROLE_LABELS: Record<Role, string> = {
  JUNAK: 'Юнак',
  VYKHOVNYK: 'Виховник',
  KURINNYI: 'Курінний',
  ZVYAZKOVYI: "Зв'язковий",
};
```

і заміна всіх місць, де роль зараз рендериться напряму (`{user.role}`),
на `{ROLE_LABELS[user.role]}` — знайти всі виклики буде окремим кроком
плану (grep по `.role}` у `apps/web`).

## Розгортання

Звичайна Prisma-міграція (`prisma migrate deploy`, вже вбудована в
команду запуску контейнера) — три нові таблиці, жодних змін до
існуючих. Розкатується тим самим `git pull && docker compose up -d
--build` на VPS, яким і зараз оновлюється бекенд. Два нові секрети
(`RESEND_API_KEY`, `FRONTEND_URL`) додаються в
`/opt/plast-api/repo/apps/api/.env` перед першим деплоєм цієї зміни.

## Тестування

Бекенд (e2e, jest):
- Зміна пароля: невірний поточний пароль → 403; вірний → пароль
  дійсно змінився (логін новим паролем працює, старим — ні).
- Forgot/reset password: повний цикл запит → лист (у тестах
  `MailService` замінюється мок-об'єктом, що перехоплює токен, а не
  реально шле листи) → скидання → логін новим паролем.
- Email change: запит → підтвердження токена → `User.email` дійсно
  змінився, старий email більше не працює для логіну.
- Самостійна зміна ПІБ юнаком: `ProfileChangeLog` отримав запис,
  `MailService.sendProfileChangeNotification` викликаний з правильним
  email виховника (мок).
- Самостійна зміна ПІБ виховником/зв'язковим: жодного запису в
  `ProfileChangeLog`, жодного листа.

Фронтенд (Playwright): повний шлях "забув пароль" — оскільки реальні
листи в тестах не шлються, `MailService` у тестовому середовищі пише
токен у відповідь тестового admin-ендпоінту (той самий патерн, що й
наявний `x-admin-key` для сідування даних) замість реальної відправки,
і e2e-тест читає токен звідти.

## Обмеження MVP (свідомі спрощення)

- Скидання пароля не завершує інші активні сесії користувача (JWT і
  так короткоживучий — 1 доба, ризик невеликий).
- Немає rate-limit на `POST /auth/forgot-password` — при потребі
  додається окремо, не блокує цей підпроєкт.
- Лист виховнику про зміну ПІБ підопічного — просто інформаційний,
  без можливості "відхилити"/оскаржити з листа. Якщо це виявиться
  недостатнім на практиці — природний кандидат для розширення в D.
