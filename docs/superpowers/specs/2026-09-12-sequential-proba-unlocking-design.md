# Послідовне відкриття проб — дизайн-документ

## Контекст і межі

Зараз усі стадії проби (`ProbyStage`, впорядковані `order`) для юнака завжди повністю відкриті одночасно — виховник/звʼязковий може підтверджувати точки будь-якої стадії в будь-якому порядку, незалежно від прогресу по попередніх стадіях. Немає жодного поняття "стадія закрита/заблокована" ні в схемі, ні в коді (підтверджено ретельним пошуком по кодовій базі).

Мета: юнак завжди починає зі стадії 1 (Прихильник) відкритою. Наступна стадія відкривається лише через явну дію виховника/зв�’язкового "Закрити пробу" на попередній — незалежно від того, чи всі точки попередньої підтверджені. Закрита стадія лишається редагованою, поки в ній є непідтверджені точки ("борг"); щойно борг закритий (усі точки підтверджені) — стадія автоматично стає read-only. "Перевідкрити пробу" повертає її в редагований стан, не забираючи доступ до вже відкритої наступної стадії.

Обидві програми проби (СТАРА і НОВА) мають по 3 стадії в однаковому порядку й з однаковими назвами — правило застосовується однаково до обох.

### Явно поза межами цього підпроєкту

- Послідовне відкриття **категорій** усередині однієї стадії — правило стосується лише цілих стадій (Прихильник → Учасник → Розвідувач), не категорій.
- Перенесення стану закриття стадій між СТАРОЮ/НОВОЮ програмою при перемиканні `Kurin.probyProgramId` — після перемикання прогрес по стадіях під новою програмою починається заново (нові `stageId`, немає рядків `JunakStageProgress`). Це узгоджено з тим, що `PointMapping` наразі не заповнений жодними даними, тож точковий прогрес і так не переноситься автоматично при перемиканні програми — нова функція не погіршує наявну поведінку.
- Міграція/бекфіл наявних даних: юнаків із реальним підтвердженим прогресом по пробах зараз немає (підтверджено Андрієм, 2026-09-12), тож спеціальної логіки для збереження чи приховування вже наявного прогресу не потрібно.

## Частина 1: Модель даних

Нова модель `JunakStageProgress` — один рядок на пару (юнак, стадія), за аналогією з `JunakProgress` на рівні точки:

```prisma
model JunakStageProgress {
  id            String    @id @default(uuid())
  junakId       String
  junak         User      @relation("JunakStageProgress", fields: [junakId], references: [id])
  stageId       String
  stage         ProbyStage @relation(fields: [stageId], references: [id])
  firstClosedAt DateTime?
  closedAt      DateTime?
  closedById    String?
  closedBy      User?     @relation("StageClosedBy", fields: [closedById], references: [id])

  @@unique([junakId, stageId])
}
```

**Чому два поля замість одного:** `firstClosedAt` — незворотний, встановлюється рівно один раз (при першому натисканні "Закрити пробу") і ніколи не скидається. Саме він визначає, чи розблокована наступна стадія. `closedAt` — поточний стан "закрита зараз/ні", який перемикається туди-сюди кнопками "Закрити пробу"/"Перевідкрити пробу". Без цього розділення "Перевідкрити" на стадії N випадково забирало б доступ до вже відкритої стадії N+1.

Рядок для стадії 1 не створюється, поки її явно не закриють — вона за замовчуванням завжди досяжна без жодного запису в базі.

### Похідні статуси (обчислюються на льоту, нічого додатково не кешується)

Для стадії N юнака J:

- **LOCKED** — N не перша стадія програми, і в рядка (J, стадія N−1) немає `firstClosedAt`.
- **OPEN** — не LOCKED, і НЕ (є рядок (J, N) з `closedAt` І всі точки стадії N підтверджені).
- **CLOSED** — не LOCKED, є рядок (J, N) з `closedAt`, і всі точки стадії N підтверджені (read-only).

"Всі точки підтверджені" — рахується як: кількість `JunakProgress` зі статусом `DONE` серед точок стадії N дорівнює загальній кількості точок стадії N.

## Частина 2: Backend API

**Нові ендпоінти** (контролер `ProbyProgressController`, ролі `VYKHOVNYK`, `ZVYAZKOVYI` — той самий guard, що й у `confirm`/`unconfirm`):

- `POST /junaky/:junakId/progress/stages/:stageId/close` — закриває стадію: `upsert` рядка `JunakStageProgress` з `closedAt = now`, `closedById = actor`, і якщо `firstClosedAt` ще не встановлено — встановлює його теж (`now`). Ідемпотентно (повторне закриття вже закритої стадії — не помилка, просто оновлює `closedAt`/`closedById`). Помилка `BadRequestException`, якщо стадія зараз LOCKED для цього юнака (закривати можна лише досяжну стадію).
- `POST /junaky/:junakId/progress/stages/:stageId/reopen` — знімає `closedAt` (встановлює `null`) у рядка `JunakStageProgress`. Дозволено лише коли обчислений статус стадії саме `CLOSED` (тобто `closedAt` встановлено І всі точки підтверджені) — інакше `BadRequestException` ("нема чого перевідкривати": стадія й так `OPEN`, або взагалі `LOCKED`). `firstClosedAt` не змінюється.

Обидва ендпоінти повторюють авторизаційні перевірки з `assertCanConfirm` (роль + призначення виховника до гуртка юнака) — той самий метод, що вже використовує `confirm`/`unconfirm`.

**Існуючі `confirm`/`unconfirm`** (`POST .../progress/:pointId/confirm|unconfirm`) отримують нову перевірку перед виконанням дії: визначити стадію точки, обчислити її статус для цього юнака; якщо статус не `OPEN` — `ForbiddenException` ("Ця проба заблокована або закрита").

**`GET /junaky/:junakId/progress`** — форма відповіді змінюється (внутрішній ендпоінт без зовнішніх споживачів, ламаюча зміна прийнятна за тим самим принципом, що й раніше в цьому проєкті):

```ts
{
  points: JunakProgress[],   // як і зараз, кожен з полем point
  stages: { stageId: string; status: 'LOCKED' | 'OPEN' | 'CLOSED' }[],  // впорядковано за stage.order
}
```

## Частина 3: Frontend

**`apps/web/app/users/[id]/page.tsx`** (перегляд виховника/звʼязкового): біля заголовка кожної стадії додається індикатор статусу і, залежно від статусу, кнопка дії (видима лише для `VYKHOVNYK`/`ZVYAZKOVYI`, як і кнопки підтвердження точок):

- `LOCKED` — стадія згорнута, приглушена, з позначкою 🔒 і підписом "Розблокується після закриття попередньої проби"; категорії всередині не розгортаються.
- `OPEN` — рендериться як і зараз (категорії/точки, кнопки підтвердження активні), плюс кнопка "Закрити пробу".
- `CLOSED` — категорії/точки видимі, але кнопки підтвердження/зняття точок сховані (read-only), плюс кнопка "🔓 Перевідкрити пробу".

**`apps/web/app/proby/page.tsx`** (власний перегляд юнака, лише перегляд): та сама логіка відображення статусів (LOCKED — згорнуто з 🔒), але без жодних кнопок дій — юнак і зараз нічого не підтверджує й не закриває сам.

## Тестування

- **Backend e2e:** `close`/`reopen` — права доступу (403 для не-виховника/звʼязкового), помилка при закритті LOCKED стадії, помилка при перевідкритті не-CLOSED стадії, ідемпотентність повторного закриття; `confirm`/`unconfirm` — 403 на точку LOCKED або CLOSED стадії; коректний розрахунок статусів LOCKED/OPEN/CLOSED у сценаріях: свіжий юнак (стадія 1 OPEN, решта LOCKED), закрита-з-боргом (стадія 1 CLOSED-статус-логічно-OPEN-бо-не-100%, стадія 2 OPEN), закрита-повністю (стадія 1 CLOSED, read-only), перевідкрита (стадія 1 знову OPEN, стадія 2 лишається OPEN).
- **Frontend Playwright:** повний сценарій — виховник бачить лише стадію 1 відкритою → підтверджує частину точок → закриває пробу (борг лишився) → бачить стадію 2 відкритою, стадія 1 досі редагована → підтверджує решту точок стадії 1 → стадія 1 стає read-only автоматично → натискає "Перевідкрити" → стадія 1 знову редагована, стадія 2 не зникає.

## Обмеження (свідомі спрощення)

- Категорії всередині стадії не мають власного порядку блокування — вся стадія відкривається/закривається одним разом.
- Перемикання програми (OLD↔NEW) скидає прогрес по стадіях під новою програмою до початкового стану — узгоджено як прийнятний наслідок відсутності даних `PointMapping`.
