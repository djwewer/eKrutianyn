# Оголошення — дизайн

**Дата:** 2026-10-08

## Контекст і проблема

Зараз у застосунку немає жодного способу централізовано повідомити весь
курінь про щось (акція, подія, новина) так, щоб кожен дізнався про це навіть
не заходячи самостійно в застосунок. Є Web Push (реалізовано попереднім
комітом, підтверджено живим тестом на iOS), але немає контенту, який би ним
розсилався — лише тестовий крон щохвилини.

Рішення: нова сутність "Оголошення" з повноцінним редактором (писар/
звʼязковий пишуть), стрічкою на новій головній сторінці (бачать усі), і
реальною push-розсилкою всім членам куреня при публікації.

## Модель даних

```prisma
model Announcement {
  id        String   @id @default(uuid())
  kurinId   String
  kurin     Kurin    @relation(fields: [kurinId], references: [id])
  authorId  String
  author    User     @relation(fields: [authorId], references: [id])
  title     String
  content   Json     // Tiptap/ProseMirror JSON-документ
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  images    AnnouncementImage[]
  reactions AnnouncementReaction[]

  @@index([kurinId, createdAt])
}

model AnnouncementImage {
  id             String        @id @default(uuid())
  // Nullable: an image is uploaded during composition, before the
  // announcement it belongs to exists — linked only once the writer
  // actually publishes (see "Бекенд: ендпоінти" below).
  announcementId String?
  announcement   Announcement? @relation(fields: [announcementId], references: [id])
  kurinId        String
  kurin          Kurin         @relation(fields: [kurinId], references: [id])
  uploaderId     String
  uploader       User          @relation(fields: [uploaderId], references: [id])
  data           Bytes
  mimeType       String
  createdAt      DateTime      @default(now())
}

enum ReactionEmoji {
  THUMBS_UP
  HEART
  CLAP
  WOW
  LAUGH
  SAD
}

model AnnouncementReaction {
  id             String        @id @default(uuid())
  announcementId String
  announcement   Announcement  @relation(fields: [announcementId], references: [id])
  userId         String
  user           User          @relation(fields: [userId], references: [id])
  emoji          ReactionEmoji
  createdAt      DateTime      @default(now())

  @@unique([announcementId, userId])
}
```

Унікальний індекс `(announcementId, userId)` на `AnnouncementReaction`
реалізує правило "одна реакція на людину": зміна емодзі — upsert
(`update` існуючого рядка на новий `emoji`), повторний клік на вже
поставлений емодзі — `delete` (зняти реакцію).

Контент зберігається як Tiptap/ProseMirror JSON (не HTML-рядок):
безпечніше (рендеримо власним рендерером Tiptap, не потрібна ручна
санітизація довільного HTML проти XSS) і дає повторне відкриття в
редакторі без втрат — відкрили JSON, отримали точно той самий стан
редактора, яким він був при збереженні.

Картинки зберігаються як `Bytes` у БД, той самий патерн, що вже є для фото
профілю (`User.photoData`) — не Google Drive (довелось би розширювати
доступ на "будь-хто з посиланням", плюс Drive без CDN гальмує при показі в
стрічці) і не окреме сховище (зайва зовнішня залежність під те, що вже
закрито DB-bytes патерном в Інвентарі/фото профілю).

## Хто що може

| Дія | Хто |
|---|---|
| Читати стрічку `/news` | Будь-який автентифікований член куреня (усі ролі) |
| Публікувати оголошення | `ZVYAZKOVYI`, або будь-хто з `KurinPosition.positionType = PYSAR` |
| Редагувати / видаляти **будь-яке** оголошення куреня | Та сама авторизація, що й публікація — не лише автор, узгоджено з користувачем явно (писар/звʼязковий діють як спільна роль діловодства, не персонально) |
| Ставити/знімати реакцію | Будь-який автентифікований член куреня |
| Отримати push при публікації нового оголошення | Усі ролі куреня (`JUNAK`, `VYKHOVNYK`, `ZVYAZKOVYI`), не лише юнаки |

## Бекенд: ендпоінти (`apps/api/src/announcements/`)

- `GET /kurins/:kurinId/announcements` — стрічка всіх оголошень куреня,
  найновіше зверху; кожен елемент включає кількість кожної реакції і
  позначку, яку (якщо є) реакцію поставив поточний користувач. Без
  пагінації у v1 (повний список одразу) — прийнятно для масштабу одного
  куреня, пагінацію можна додати пізніше, якщо стрічка стане завеликою.
- `POST /kurins/:kurinId/announcements` (body `{title, content, imageIds}`)
  — **публікує** оголошення одразу з повним текстом (жодної видимої для
  всіх порожньої чернетки) і одразу шле push усьому куреню (див. нижче).
  `imageIds` — список id картинок, завантажених під час композиції (крок
  нижче), які прив'язуються до цього оголошення.
- `PATCH /kurins/:kurinId/announcements/:id` (той самий body) — оновити
  вже опубліковане оголошення.
- `DELETE /kurins/:kurinId/announcements/:id` — видалити (каскадно видаляє
  `images`/`reactions` цього оголошення).
- `POST /kurins/:kurinId/announcements/images` (multipart, ліміт
  10MB/файл, `image/*` mimetype — як вже в Інвентарі) — завантажити
  картинку **під час композиції, до публікації**: зберігається одразу
  (`announcementId: null`), повертає `{id, url}` для вставки image-ноди в
  Tiptap. Прив'язка до конкретного оголошення (`announcementId`)
  проставляється на бекенді, коли той самий `id` приходить у масиві
  `imageIds` при `POST`/`PATCH` оголошення.
- `GET /kurins/:kurinId/announcements/images/:imageId` — віддає байти
  картинки (публічний для автентифікованих членів куреня, як і фото
  профілю).
- `PUT /kurins/:kurinId/announcements/:id/reactions` (body `{emoji}`) —
  поставити/замінити власну реакцію (upsert).
- `DELETE /kurins/:kurinId/announcements/:id/reactions` — зняти власну
  реакцію.

Авторизація створення/редагування/видалення: `actor.role === 'ZVYAZKOVYI'
|| actor.positions.includes('PYSAR')`, той самий патерн перевірки, що вже
використовується для `INTENDANT`/`SUDDIA`/`SKARBNYK` в `nav.tsx` і
відповідних контролерах.

## Push-інтеграція

Розширюю вже наявний `PushNotificationsService` (попередній комміт) новим
методом `sendToKurin(kurinId, payload)`: фільтрує `PushSubscription` за
`userId IN (SELECT id FROM "User" WHERE kurinId = ...)`, а не глобально
по всіх підписках, як робив тестовий крон. Той самий механізм підчищення
мертвих підписок на 404/410 (`sendAndPruneIfGone`) перевикористовується
без змін.

Payload: `{ title: 'Нове оголошення', body: announcement.title, url: '/news' }`.
Відправка — синхронно всередині того самого запиту, що публікує оголошення
(`POST /announcements`, яке одразу містить повний текст — жодної проміжної
порожньої чернетки немає), одразу після успішного запису в БД.

**Тестовий крон-щохвилини (`PushNotificationsCron`) видаляється повністю**
— свою роль він відіграв (підтверджено живим тестом на iOS), реальні
сповіщення тепер шле сама подія публікації оголошення.

## Фронтенд

**Редактор** (`apps/web/app/news/new/page.tsx`, доступ лише писарю/
звʼязковому):
- Поле "Заголовок" (окремо від тіла).
- Tiptap-редактор з розширеннями `StarterKit` (параграфи, H1/H2/H3,
  жирний/курсив, марковані/нумеровані списки), `Link` (виділив текст →
  вставив URL), власне `Image`-розширення, що при вставці файлу одразу
  шле `POST .../announcements/images` і вставляє ноду з отриманим URL.
  Увесь текст (заголовок + тіло) до натискання "Опублікувати" існує лише
  в стані редактора на клієнті — нічого не зберігається і нікому не видно.
- Кнопка "Опублікувати" (нове оголошення) збирає `{title, content,
  imageIds}` (зі списку id картинок, вставлених у цю сесію редагування) і
  шле один `POST /announcements` — це й створює рядок, і шле push.
  Сторінка редагування вже опублікованого натомість шле `PATCH .../:id`
  з тим самим тілом, кнопка підписана "Зберегти".

**Стрічка** (`apps/web/app/news/page.tsx`):
- Картки, найновіше зверху: заголовок, автор + дата, Tiptap read-only
  рендер вмісту (картинки інлайн), ряд із 6 емодзі-кнопок (лічильник на
  кожній, власна реакція підсвічена; клік на іншу — заміна, клік на вже
  активну — зняття).
- Якщо поточний користувач — писар/звʼязковий: кнопки "Редагувати"/
  "Видалити" на кожній картці (не лише на своїх).

**Навігація:**
- `nav.tsx`: `<h1>` з назвою куреня обгортається в `<Link href="/news">`.
- Пункт "Оголошення" додається першим у кожен масив `LINKS_BY_ROLE`.
- `app/page.tsx`: прибирається `HOME_BY_ROLE`-розведення по ролях; `/`
  редіректить усіх автентифікованих користувачів на `/news`.

## Обробка помилок

- Порожній заголовок чи контент — блокується і на фронті (кнопка
  неактивна), і на бекенді (`@IsNotEmpty` на DTO).
- Картинка не того типу/завелика — `FileTypeValidator`/`fileFilter` на
  контролері, той самий патерн, що в `inventory.controller.ts`.
- Невдала відправка push одній підписці (мертвий токен) не блокує
  відправку іншим — вже вирішено в `PushNotificationsService`, нічого
  додатково робити не треба.
- Гонка двох швидких кліків на реакцію одним користувачем — вирішується
  unique-constraint `(announcementId, userId)` + upsert на рівні БД.
- 403 при спробі створити/редагувати/видалити без прав писаря/звʼязкового
  — стандартний `ForbiddenException`, як і в інших захищених ендпоінтах.

## Тестування

- Юніт-тести `AnnouncementsService`: створення/редагування/видалення з
  правильною авторизацією (писар, звʼязковий — дозволено; юнак без позиції,
  вихованець — 403), upsert/заміна/зняття реакції, фільтрація стрічки по
  `kurinId`.
- Юніт-тест нового `PushNotificationsService.sendToKurin`: шле лише
  підпискам з потрібним `kurinId`, не чіпає підписки інших куренів.
- Playwright e2e: звʼязковий чи писар публікує оголошення з картинкою →
  воно зʼявляється в стрічці `/news` з картинкою → реакція ставиться і
  знімається повторним кліком → юнак без позиції писаря не бачить кнопок
  редагування.
- Саму фактичну доставку push у e2e не перевірити — той самий виняток,
  що й для попередньої фічі Web Push (цей сандбокс блокує egress до
  Google push-сервісів); перевіряється лише що `sendToKurin` викликається
  з правильним payload і що мертві підписки підчищаються.

## Явно поза скоупом (можливі майбутні ітерації, не зараз)

- Анкор-скрол до конкретного оголошення при кліку на push-сповіщення
  (зараз просто відкриває `/news`, без автоскролу до нового запису).
- Довільний емоджі-пікер замість фіксованого набору з 6.
- Таргетинг оголошень на конкретний гурток чи роль (зараз — завжди весь
  курінь).
- Прибирання "сирітських" картинок: якщо писар завантажив картинку в
  редакторі, а тоді закрив вкладку, не натиснувши "Опублікувати" —
  `AnnouncementImage` з `announcementId: null` лишається в БД назавжди
  (місце з часом накопичується, але повільно — під масштаб одного куреня
  не критично). Періодичне прибирання такого сміття (крон, що видаляє
  сирітські картинки старші за N днів) можна додати пізніше, якщо
  виявиться реальною проблемою.
