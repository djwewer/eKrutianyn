# Курінний проходить пробу — дизайн-документ

## Контекст і межі проєкту

Курінний — це, по суті, юнак із розширеними правами: він так само проходить
власну пробу, як і будь-який інший юнак куреня. Наявний бекенд цього не
підтримує: `User.role` одночасно визначає і рівень доступу
(JUNAK/VYKHOVNYK/KURINNYI/ZVYAZKOVYI), і "чи ця людина має трекований
прогрес проби" — `proby-progress.service.ts` жорстко вимагає
`role === JUNAK` скрізь, де йдеться про прогрес. Курінний зараз отримує
`404`/`403` на всі проби-пов'язані дії, включно з переглядом власного
прогресу.

Це маленький, точковий фікс — виявлений під час брейнштормінгу фронтенду
(`2026-08-29-frontend-design.md`), який уже покладається на його
результат (екран `/proby` для курінного).

### Явно поза межами цього підпроєкту

- Виховник і зв'язковий пробу не проходять — це стосується лише курінного.
- Жодних змін до схеми БД (`User.role` лишається єдиним enum-полем, без
  нового `tracksProby`-подібного поля — обґрунтування нижче).
- Майбутні додаткові ролі-надбудови над юнаком (заступник курінного,
  писар, скарбник) — лише зафіксовано як майбутній напрямок в
  "Обмеження MVP", не проєктується зараз.

## Механізм

Нова спільна константа в `apps/api/src/common/proby-tracking-roles.ts`:

```ts
import { Role } from '@prisma/client';

export const PROBY_TRACKING_ROLES: Role[] = [Role.JUNAK, Role.KURINNYI];
```

**Чому константа, а не нове поле в БД:** розробник(-ка) підтвердив(-ла),
що "курінний проходить пробу" — структурна властивість самої ролі
(кожен курінний завжди був і лишається юнаком), а не індивідуальний
прапорець, який комусь треба буде вмикати/вимикати вручну. Розширення
переліку ролей у```role === JUNAK```-перевірках — найменша зміна, що
покриває це без міграції БД. Якщо пізніше з'явиться потреба в
per-user гнучкості (не прив'язаній до ролі) — тоді й буде сенс переходити
на окреме поле.

### Зміна 1: `proby-progress.service.ts` → `getProgressFor`

Дві окремі перевірки потребують зміни:

1. **Цільова перевірка** (чи цей `junakId` взагалі може мати прогрес) —
   зараз `junak.role !== Role.JUNAK`, стає
   `!PROBY_TRACKING_ROLES.includes(junak.role)`.
2. **Перевірка запитувача-курінного** — зараз курінний повністю
   заблокований незалежно від того, чий прогрес запитує:
   ```ts
   if (actor.role === Role.KURINNYI) {
     throw new ForbiddenException('Kurinnyi cannot view proby progress');
   }
   ```
   Замінюється на дзеркальне до вже наявного правила для юнака (юнак
   бачить лише власний прогрес):
   ```ts
   if (actor.role === Role.KURINNYI && actor.userId !== junakId) {
     throw new ForbiddenException('Kurinnyi cannot view another user\'s proby progress');
   }
   ```
   Курінний, що запитує власний `junakId === actor.userId`, проходить далі
   (минаючи й перевірку виховника, бо вона застосовується лише при
   `actor.role === Role.VYKHOVNYK`) — і одразу отримує свій прогрес.

### Зміна 2: `proby-progress.service.ts` → `assertAssignedVykhovnyk`
(спільний приватний хелпер для `confirm`/`unconfirm`)

Та сама цільова перевірка розширюється:
`junak.role !== Role.JUNAK` → `!PROBY_TRACKING_ROLES.includes(junak.role)`.

**Виправлення припущення (2026-08-29, після фінального рев'ю):** початкова
версія цього документа помилково вважала курінного типово безгурткови́м і
покладалась на механізм "будь-який виховник куреня підтверджує безгурткового
юнака" (`hurtokId: junak.hurtokId ?? undefined`). Це неправильно: **курінний
— повноцінний юнак, який завжди перебуває в конкретному гуртку, як і будь-
який інший юнак; курінний ніколи не буває поза гуртком.** Тому підтверджувати
й далі може лише виховник (`@Roles(Role.VYKHOVNYK)` на контролері, без змін),
**призначений саме на гурток цього курінного** — точнісінько той самий шлях,
що вже й так працює для юнака, без жодної спеціальної гілки логіки. Це
означає дві додаткові зміни поза `proby-progress.service.ts`, потрібні, щоб
"курінний завжди в гуртку" виконувалось на практиці:

### Зміна 3: `users.service.ts` → `create()`

Наразі `hurtokId` обов'язковий лише для `role === Role.JUNAK`:
```ts
if (dto.role === Role.JUNAK && !dto.hurtokId) {
  throw new BadRequestException('hurtokId is required for JUNAK role');
}
```
Розширюється на весь `PROBY_TRACKING_ROLES` — курінного не можна створити
без гуртка, так само як юнака.

### Зміна 4: `hurtky.service.ts` → `getBoard()`

Дошка гуртка (`GET /hurtky/:id/board`, з read-API-плану) наразі показує
лише `role: Role.JUNAK`. Розширюється на
`role: { in: PROBY_TRACKING_ROLES } }`, щоб курінний з'являвся на дошці
свого гуртка поряд зі звичайними юнаками — це і є спосіб, яким виховник
"знаходить" курінного, щоб підтвердити йому точку (без цього виховник фізично
не мав би де побачити курінного — саме цю прогалину знайшло фінальне
рев'ю). Ніяких змін до `GET /users?role=` чи інших правил видимості
курінного з read-API-плану не потрібно — ця прогалина закривається виключно
через дошку гуртка.

### Зміна 5: `kurins.service.ts` → `changeProbyProgram`

Запит юнаків для міграції "здано"-точок при зміні програми проб куреня:
`where: { kurinId, role: Role.JUNAK }` →
`where: { kurinId, role: { in: PROBY_TRACKING_ROLES } }`.

Без цієї зміни прогрес курінного мовчки не переноситься при зміні
програми проб — точки лишаються прив'язані до старої програми назавжди.

## Тестування

e2e-тести (той самий підхід, що і в решті кодбази — supertest + fixtures
+ реальна тестова БД):

1. Курінний бачить власний прогрес проби (`GET /junaky/:ownId/progress` →
   200).
2. Курінний НЕ бачить прогрес іншого користувача (свого чи іншого
   курінного, чи юнака) — 403.
3. Юнак і зв'язковий продовжують працювати як раніше (регресія: юнак —
   лише свій прогрес; зв'язковий — будь-чий).
4. **Виховник, призначений на гурток курінного**, підтверджує йому точку —
   `POST .../confirm` → 200 (той самий тест-патерн, що й для юнака —
   курінний з `hurtokId`, а не безгуртковий).
5. Виховник, НЕ призначений на гурток курінного (навіть якщо в тому ж
   курені), НЕ може підтвердити — 403 (той самий тест-патерн, що вже є
   для юнака).
6. Виховник з іншого куреня НЕ може підтвердити точку курінному —
   404 (tenant isolation, регресія наявної поведінки).
7. `POST /users` вимагає `hurtokId` для `role: KURINNYI`, як і для JUNAK —
   400 без нього.
8. `GET /hurtky/:id/board` показує курінного серед `junaky` поряд зі
   звичайними юнаками цього гуртка.
9. Зміна програми проб куреня переносить "здано"-точки курінного так само,
   як і юнаків (регресійний + новий кейс в `kurins-proby-program.e2e-spec.ts`).

## Обмеження MVP (свідомі спрощення)

- **Лише курінний, не виховник/зв'язковий.** Підтверджено користувачем —
  ці дві ролі пробу не проходять у цій системі.
- **Немає окремого поля для гнучкості на рівні конкретної людини** — див.
  "Механізм" вище. Якщо потреба з'явиться, це вже інша задача.
- **Майбутні ролі-надбудови над юнаком** (заступник курінного, писар,
  скарбник) — розробник(-ка) прямо зазначив(-ла), що це заплановано:
  "всі вони — юнаки, мають мати базовий функціонал, а зверху накидуємо
  додаткові обов'язки". Коли ці ролі з'являться, `PROBY_TRACKING_ROLES`
  доведеться розширювати вручну знову — і, ймовірно, назріє ширший
  перехід від одного enum `role` до моделі "базова роль (юнак/виховник) +
  список додаткових обов'язків". Не проєктується зараз — лише
  зафіксовано, щоб не було несподіванкою для майбутнього плану.
