# Контакти опікунів — дизайн-документ

## Контекст і межі

Роадмап-пункт E. Зараз `User` має власні поля `phone`/`notes` — це контакти самого юнака (редагуються через `PATCH /users/:id/contact-info`), не його батьків/опікунів. Концепції "опікун юнака" в системі немає взагалі.

Мета — проста телефонна книга: зв'язковий чи курінний бачить, кому дзвонити щодо конкретного юнака (у екстреній ситуації, для запрошення на батьківські збори тощо). Без робочих процесів (дозволи, підписи, погодження) — лише довідник контактів.

### Явно поза межами

- Жодних процесів погодження/дозволів від опікунів (підписи, електронні згоди) — лише зберігання контактної інформації.
- Жодного окремого логіну/порталу для опікунів — вони не користувачі системи.
- Позначка "головний опікун" — усі записи рівноцінні.
- Доступ для виховників — свідомо не додається (нижче).

## Дані

Нова модель, список 0..N записів на юнака:

```prisma
model GuardianContact {
  id        String   @id @default(uuid())
  junakId   String
  junak     User     @relation("JunakGuardians", fields: [junakId], references: [id])
  name      String
  phone     String
  role      String?
  email     String?
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}
```

`name`/`phone` обов'язкові; `role` (вільний текст: "Мама"/"Тато"/"Бабуся" тощо) і `email` — опційні. Додати `guardianContacts GuardianContact[] @relation("JunakGuardians")` до `User`. Чисто адитивна міграція (нова таблиця, новий relation-рядок у `User`) — прод має живі дані, тому без `ALTER` наявних колонок.

## Бекенд

Новий модуль (або розширення `users`) з ендпоінтами під `/users/:id/guardian-contacts`:

- `GET /users/:id/guardian-contacts` — список опікунів юнака.
- `POST /users/:id/guardian-contacts` — додати запис (`{ name, phone, role?, email? }`).
- `PATCH /users/:id/guardian-contacts/:guardianId` — редагувати будь-яке з полів.
- `DELETE /users/:id/guardian-contacts/:guardianId` — видалити запис.

**Доступ** — та сама перевірка, що вже діє для `updateContactInfo` (`apps/api/src/users/users.service.ts`): `actor.role === Role.ZVYAZKOVYI || actor.isKurinniy`, і цільовий `:id` має бути `role === Role.JUNAK` у курені актора. Виховник доступу не отримує — ні на перегляд, ні на редагування (свідоме рішення, узгоджене під час брейнштормінгу).

Кожен ендпоінт додатково перевіряє, що `guardianId` (для PATCH/DELETE) належить саме юнаку `:id`, а не якомусь іншому — інакше 404.

## Фронтенд

Новий розділ "Опікуни" на сторінці `/users/[id]/page.tsx`, видимий за тим самим прапорцем `canEditContactInfo`, що вже ховає/показує contact-info юнака. Список карток (ім'я, роль, телефон, email), кнопки "Редагувати"/"Видалити" на кожній, форма додавання нового запису знизу списку.

`lib/queries/guardian-contacts.ts`: `useGuardianContacts(junakId)`, `useAddGuardianContact(junakId)`, `useUpdateGuardianContact(junakId)`, `useRemoveGuardianContact(junakId)` — той самий TanStack Query паттерн, що й у решті `lib/queries/`.

## Тестування

Бекенд (e2e): зв'язковий/курінний додає/редагує/видаляє запис опікуна; юнак без посади курінного отримує 403; спроба додати опікуна юнаку з іншого куреня — 404; PATCH/DELETE з `guardianId`, що належить іншому юнаку — 404.

Фронтенд (Playwright): зв'язковий додає опікуна на сторінці юнака, бачить його в списку, редагує телефон, видаляє запис.

## Обмеження (свідомі спрощення)

- Немає валідації формату телефону/email — прості текстові поля.
- Немає історії змін цих записів (на відміну від `ProfileChangeLog` для власних даних юнака) — редагування/видалення остаточне.
