# Реальний вміст проби (стара програма) + вибір програми куреня — дизайн-документ

## Контекст і межі

`ProbyProgramVersion.OLD` зараз має один `ProbyProgram` у базі з плейсхолдер-вмістом (`ProbyStage`/`ProbyCategory`/`ProbyPoint` на кшталт "Stage 1"/"Category 1") — так само, як мала `NEW` до підпроєкту "реальний вміст проби (нова програма)" (`docs/superpowers/specs/2026-09-09-proby-content-design.md`, `docs/superpowers/plans/2026-09-09-real-proby-content.md`). Цей підпроєкт — паралельна робота для СТАРОЇ програми.

Andrii підтвердив (2026-09-12): СТАРА і НОВА — це дві окремі, паралельні програми проби, що співіснують; частина куренів уже працює по старій, частина по новій. Вміст СТАРОЇ програми **не є дублікатом** уже завантаженого вмісту НОВОЇ, попри однакові історичні назви рангів ("Скобине крило", "Скобиний хват") — наповнення точок відрізняється.

Andrii надав 3 PDF у локальній, поза-git папці `ПРОБИ  старі/` (два пробіли в назві) у корені репозиторію:

- `1_skobyne_krylo_div_kolir.pdf` — «Скобине крило», перша проба УПЮ, **тільки дівочий варіант**
- `2_skobynyy-hvat_hl_chb.pdf` — «Скобиний хват», друга проба УПЮ, **тільки хлопчачий варіант**
- `prykhylnyk-2.pdf` — «Відзнака прихильника», плаский список вимог без категорій

На відміну від підпроєкту НОВОЇ програми (де для кожного рівня були надані обидві статеві версії), тут надано лише по одному файлу на рівень. Andrii підтвердив: завантажуємо рівно те, що є, не чекаючи відсутніх пар (дівочий "Скобиний хват", хлопчачий "Скобине крило").

### Явно поза межами цього підпроєкту

- `PointMapping` (мапінг еквівалентних точок між СТАРОЮ і НОВОЮ програмою для безпечного перенесення прогресу юнака при зміні програми куреню) — не заповнюється зараз. Andrii підтвердив, що це знадобиться в майбутньому (записано окремим пунктом у `docs/backlog.md`), але вимагає реального вмісту обох програм, тому виконується окремим підпроєктом пізніше.
- Обмеження адмін-каталогу до "рівно двох стандартних програм" — окремий пункт `docs/backlog.md`, не тут.
- "Скобиний лет" (третя проба УПЮ) — не має точкової структури (проєктна робота, не чекбокси), файл не надавався — поза межами, як і для НОВОЇ.
- Послідовне відкриття проб (юнак бачить/підтверджує тільки одну активну пробу за раз) — окремий пункт `docs/backlog.md`, не пов'язаний із завантаженням контенту.

## Частина 1: Дані — три стадії в `ProbyProgram(OLD)`

Наявна модель (`ProbyProgram → ProbyStage → ProbyCategory → ProbyPoint`) підходить без зміни схеми. Три рівні стають трьома `ProbyStage` за порядком у тому самому `ProbyProgram(version=OLD)`:

| `order` | `ProbyStage.name` | Категорій | Точок (орієнтовно) |
|---|---|---|---|
| 1 | "Проба прихильника (Відзнака прихильника)" | 1 ("Точки") | 13 |
| 2 | "Проба учасника (Скобине крило)" | 8 (А–Є) | ~50 |
| 3 | "Проба розвідувача (Скобиний хват)" | 7 (А–Е) | ~40 |

Точні числа точок звіряються дослівно з текстом PDF під час написання й виконання плану (не фіксуються тут остаточно — так само, як і в дизайні НОВОЇ програми).

**Рівень 1 (Проба прихильника)** — у джерелі плоский список без категорій. Усі точки лягають в одну категорію "Точки", як і аналогічний рівень НОВОЇ програми.

**Рівні 2 і 3** мають лише одну статеву версію кожен (рівень 2 — дівоча, рівень 3 — хлопчача) — завантажуються як є, без статевого розділення в базі (модель `ProbyPoint` й так не має поля статі).

## Частина 2: Механізм завантаження

Одноразовий TS-скрипт `apps/api/src/scripts/seed-real-proby-content-old.ts` (окремий файл, аналог `seed-real-proby-content.ts` для NEW, з даними в окремому `apps/api/src/scripts/real-proby-content-old.data.ts`):

1. Знаходить `ProbyProgram` з `version: OLD` — падає з чіткою помилкою, якщо не рівно один (нема куди писати).
2. Видаляє поточне піддерево `ProbyStage → ProbyCategory → ProbyPoint` цієї програми.
3. Вставляє нове піддерево трьома стадіями за порядком із точним текстом із PDF.
4. `ProbyProgram.id` не змінюється.

**Без додаткових перевірок і обмежень** — на відміну від скрипта для NEW (який захисно перевіряв відсутність `JunakProgress`/`PointMapping`), цей скрипт для OLD виконує пряме перезаписування без guard-перевірок, за явним рішенням Andrii (2026-09-12: "Стару пробу просто переписуємо, без жодних обмежень і перевірок").

Скрипт запускається вручну: спершу проти локальної dev-бази для перевірки, потім проти продакшн-бази на VPS — точний спосіб виконання визначає план виконання (як і для NEW).

## Частина 3: Вибір програми куреня — заміна UUID на простий вибір

Зараз `/kurin` (сторінка звʼязкового) вимагає вручну ввести сирий UUID цільової `ProbyProgram` у текстове поле (`ChangeProbyProgramDto.newProgramId: string`) і показує поточну програму як голий UUID (`Поточна програма: {kurin.probyProgramId}`) — незручно й крихко, той самий клас проблеми, що вже виправляли для номера куреня.

**Бекенд:**
- `ChangeProbyProgramDto` замінює `newProgramId: string` (`@IsUUID`) на `version: ProbyProgramVersion` (`@IsEnum(ProbyProgramVersion)`).
- `KurinsService.changeProbyProgram` шукає цільову програму через `this.prisma.probyProgram.findFirst({ where: { version } })` замість `findUnique({ where: { id } })`; 404, якщо програми такої версії не існує. Уся наявна логіка перенесення прогресу (`PointMapping`, `doneOldEntries` тощо) лишається без змін — змінюється лише спосіб визначення цільової програми, не сам процес зміни.
- `GET /kurins/:id` (і будь-який ендпоінт, що повертає курінь із програмою) має віддавати достатньо даних, щоб фронтенд показав "Стара"/"Нова" замість UUID — включити `probyProgram: { version }` у відповідь (точна форма — деталь виконання плану).

**Фронтенд (`apps/web/app/kurin/page.tsx`):**
- Текстове поле "ID нової програми" замінюється вибором (radio/select) із двох варіантів: "Стара програма" / "Нова програма", з візуальним позначенням поточної.
- "Поточна програма: {UUID}" замінюється на "Поточна програма: Стара"/"Нова" (за `kurin.probyProgram.version`).
- Кнопка зміни програми відкриває `window.confirm()` з попередженням про вплив на прогрес юнаків перед відправкою запиту (найлегший спосіб підтвердження — у застосунку ще немає компонента AlertDialog, а `window.confirm` вже not used elsewhere but is the standard lightweight browser-native choice for a rare, low-frequency destructive-ish action).

## Тестування

- **Скрипт завантаження:** запуск проти чистої/dev-бази, підрахунок кількості стадій/категорій/точок після виконання, звірка кількох випадкових точок дослівно з PDF.
- **Зміна програми куреня:** оновити існуючий `apps/api/test/*kurins*.e2e-spec.ts` (метод зміни програми) під нову форму DTO (`version` замість `newProgramId`) — та ж бізнес-логіка, новий вхідний формат. Playwright-тест `apps/web/e2e/kurin-settings.spec.ts` оновлюється під нову UI-взаємодію (вибір версії + `window.confirm`) замість заповнення текстового поля UUID.
- E2e-тести проби (`apps/api/test/*proby*.e2e-spec.ts`) не зачіпаються — вони будують власне ізольоване дерево через фікстуру `createProbyProgramTree`, незалежно від реального вмісту OLD/NEW.

## Прибирання файлів

Локальна папка `ПРОБИ  старі/` лишається на місці після запуску скрипта. Видаляється лише після того, як Andrii сам перевірить завантажений вміст у застосунку (сторінка `/proby` для куреня на СТАРІЙ програмі) — так само, як і для НОВОЇ програми.

## Обмеження (свідомі спрощення)

- Точна кількість точок у "Проба учасника" і "Проба розвідувача" — орієнтовна, остаточне число залежить від повної звірки тексту в плані виконання.
- Рівні 2 і 3 мають лише по одній статевій версії кожен (не обидві, як для NEW) — завантажується те, що надано.
- Немає способу відкотити завантаження назад до плейсхолдера — ручна операція з бекапу бази, поза межами цього підпроєкту.
- Зміна DTO `ChangeProbyProgramDto` — не зворотньо сумісна зміна контракту (`newProgramId` → `version`); оскільки це внутрішній ендпоінт застосунку (не публічне API), сумісність зі старими клієнтами не потрібна.
