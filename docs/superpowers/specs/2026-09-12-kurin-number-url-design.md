# Номер куреня замість raw id в URL — дизайн-документ

## Контекст і межі

Щойно завершений підпроєкт "Гурток → юнак → проба" дав конкретному гуртку людяний URL — `/[kurinId]/hurtky/[slug]` — але сегмент куреня досі raw UUID. Мета цього підпроєкту — замінити його на вже наявне поле `Kurin.kurinNumber` (реальний пластовий номер куреня, наприклад "75"), щоб URL виглядав як `/75/hurtky/vovky`.

По ходу брейнштормінгу виявилась суміжна проблема: `kurinNumber` зараз обов'язкове текстове поле без перевірки унікальності, і підготовчі курені (реальна пластова категорія) не мають офіційного номера на момент створення. Це стало другою частиною підпроєкту.

### Явно поза межами

- Людяний слаг для самого гуртка — вже є з попереднього підпроєкту, не чіпається.
- Жодних змін в авторизації бекенду — `[kurinNumber]` в URL і надалі декоративний, усі API-запити скеровуються за `kurinId` з JWT, як і раніше.

## Дані

`Kurin.kurinNumber` отримує `@@unique` на рівні схеми Prisma. Продакшн має один реальний курінь (номер "75") — конфліктів під час міграції не буде.

## Створення куреня (адмін-API)

`kurinNumber` у `CreateKurinDto` стає опційним. Якщо не переданий — `KurinsAdminService.createKurin` сам підбирає наступний вільний номер у форматі `"П-N"` (шукає максимальний існуючий `П-*` серед усіх куренів, бере `N+1`; якщо жодного `П-*` ще нема — починає з `"П-1"`). Префікс `П` (підготовчий) візуально відрізняє тимчасові номери від реальних пластових.

## Самостійна зміна номера

Новий ендпоінт `PATCH /kurins/:id/kurin-number` (`{ newNumber: string }`), доступний лише зв'язковому і лише для власного куреня — той самий патерн доступу, що вже є в `PATCH /kurins/:id/proby-program`. Зв'язковий може вводити будь-яке значення в будь-який момент (перехід з "П-N" на реальний номер, чи виправлення описки) — без обмежень на формат чи одноразовість переходу. Спроба встановити номер, який уже зайнятий іншим куренем, повертає 409.

На сторінці `/kurin` поле "Номер" стає редагованим (вхідне поле + кнопка "Змінити", видимі лише зв'язковому) — той самий UI-патерн, що вже є для зміни програми проб на цій сторінці.

## Токен і сесія

`kurinNumber` додається до JWT-payload за тим самим принципом, що й `isKurinniy` з підпроєкту "Діловоди": рахується з бази при вході (`loginWithPassword`/`loginWithGoogle`), кладеться в токен винятково для того, щоб фронтенд міг миттєво зібрати URL без зайвого запиту. Це не джерело істини для авторизації — бекенд і надалі перевіряє все за `kurinId`. Якщо зв'язковий змінює номер куреня, у токені лишається старе значення до наступного входу (та сама допустима застарілість, що й для `isKurinniy`).

## Фронтенд

- Параметр маршруту перейменовується з `[kurinId]` на `[kurinNumber]`: `apps/web/app/[kurinId]/hurtky/[slug]/page.tsx` → `apps/web/app/[kurinNumber]/hurtky/[slug]/page.tsx`.
- `apps/web/app/hurtky/page.tsx` — посилання на гурток тепер `/${session?.kurinNumber}/hurtky/${h.slug}` замість `/${session?.kurinId}/hurtky/${h.slug}`.
- `apps/web/app/kurin/page.tsx` — редагування номера, як описано вище.

## Тестування

Бекенд (e2e): створення куреня без `kurinNumber` дає `"П-1"`; друге створення без номера дає `"П-2"`; спроба створити курінь з номером, який уже зайнятий, — 409 (чи відповідна помилка бази, оброблена як 409); зв'язковий змінює номер на новий унікальний — успіх; зв'язковий намагається встановити номер іншого куреня — 409; не-зв'язковий не може змінити номер — 403; зв'язковий іншого куреня не може змінити чужий номер — 403/404.

Фронтенд (Playwright): зв'язковий заходить на `/kurin`, бачить поточний номер, змінює його, бачить оновлене значення; посилання на гурток зі сторінки `/hurtky` веде на URL з новим номером.

## Обмеження (свідомі спрощення)

- Немає історії зміни номера куреня — просто перезапис поля.
- Немає окремого workflow "запит на офіційний номер від організації" в самому застосунку — це організаційний процес поза межами додатку; застосунок лише дозволяє вписати отриманий номер.
