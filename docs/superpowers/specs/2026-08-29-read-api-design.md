# Read API для "Ядро + Проби" — дизайн-документ

## Контекст і межі проєкту

Бекенд "Ядро + Проби" (19 задач, див. `2026-08-28-yadro-proby-design.md` та
`2026-08-28-yadro-proby-backend.md`) реалізує лише write-операції та кілька
вузьких read-ендпоінтів (`GET /users/me`, `GET /hurtky`,
`GET /junaky/:junakId/progress`, `GET /approval-requests`). Каталог проб
(програми/ступені/категорії/точки) читається лише через `AdminKeyGuard`
(платформний bootstrapping), недоступний звичайним користувачам через JWT.
Без повноцінного read-API фронтенд не може бути побудований — жоден екран
(навіть простий список юнаків чи чекліст проб) не має звідки брати дані.

Цей підпроєкт додає read-only GET-поверхню поверх існуючої моделі даних і
ролей. Нових таблиць, бізнес-логіки чи змін до write-шляхів не додається.

### Явно поза межами цього підпроєкту

- Будь-які write-операції (уже реалізовані в "Ядро + Проби").
- Наповнення каталогу проб реальними даними (окрема задача).
- Пагінація (see "Обмеження MVP").
- Фронтенд.
- Дашборди/аналітика поза описаними в цьому документі ендпоінтами.

## Архітектура

Розширення існуючих модулів — кожен ресурс отримує `GET`-методи поруч зі
своїми наявними `POST`/`PATCH`, за тим самим патерном: `JwtAuthGuard` +
`RolesGuard` (де потрібне обмеження ролі) + `@CurrentUser()` для
тенант-скоупінгу + Prisma `select`-whitelist (без `passwordHash`/`googleId`).
Один новий метод у `proby-catalog` для звичайного JWT-читання каталогу
(окремо від наявного admin-контролера). Одна нова агрегована view —
`GET /hurtky/:id/board`.

Ізоляція тенантів — той самий патерн, що і в решті кодбази: усі query
скоповані по `actor.kurinId` з JWT, ніколи з client input.

## Ендпоінти

### 1. Каталог проб

`GET /proby-programs/current`

- Доступ: усі 4 ролі (JUNAK, VYKHOVNYK, KURINNYI, ZVYAZKOVYI).
- Повертає: дерево програми проб, що зараз активна для куреня користувача
  (`Kurin.probyProgramId`) — program → stages → categories → points.
- Не показує інші програми (наприклад, стару версію, якщо курінь уже
  мігрував) — лише поточну.

### 2. Дані куреня

`GET /kurins/me`

- Доступ: усі 4 ролі.
- Повертає: `id`, `name`, `kurinNumber`, `gender`, `stanytsia`,
  `probyProgramId` для куреня поточного користувача (`actor.kurinId`).

### 3. Список користувачів

`GET /users?role=&hurtokId=`

- Query-фільтри опціональні: `role` (JUNAK | VYKHOVNYK | KURINNYI |
  ZVYAZKOVYI), `hurtokId`.
- Видимість за роллю запитувача (переглянуто під час імплементації Task 3
  — курінний тепер бачить, але не редагує, виховників і зв'язкового;
  зв'язковий бачить усіх, бо він їх призначає й керує їхніми акаунтами):
  - **JUNAK**: 403 (список недоступний, юнак використовує `GET /users/me`).
  - **VYKHOVNYK**: лише юнаки гуртків, до яких призначений (+ безгурткові
    юнаки — консистентно з рулінгом Task 13 в основному дизайні: виховники
    мають бачити й підписувати точки безгуртковим юнакам, навіть не бачачи
    їх "у форматі гуртка"). Будь-яке інше значення `role` — 403.
  - **KURINNYI**: юнаки куреня (за замовчуванням, без фільтра), а також
    виховники та зв'язковий за явним `?role=VYKHOVNYK`/`?role=ZVYAZKOVYI`
    (лише перегляд — жодних прав на редагування цих ролей, тому
    `PATCH /users/:id/contact-info` для них лишається недоступним).
    `?role=KURINNYI` — 403 (курінний не бачить інших курінних).
  - **ZVYAZKOVYI**: усі користувачі куреня незалежно від ролі. Без фільтра
    — повний список (усі 4 ролі); будь-яке значення `role` дозволене.
  - Комбінація `?role=VYKHOVNYK&hurtokId=` завжди повертає порожній
    список: `hurtokId` — це пряме поле лише в юнаків, виховники
    прив'язані до гуртка через окрему таблицю призначень. Свідомо
    залишено як є — список виховників гуртка є через
    `GET /vykhovnyk-assignments?hurtokId=` (не через `board` — `board`
    повертає лише юнаків, виховників не включає).
  - Результат відсортований по `lastName`, потім `firstName` — щоб порядок
    не змінювався між однаковими запитами (додано після фінального рев'ю
    2026-08-29, до того порядок був недетермінований).
- Whitelist полів — 9 базових полів (без `passwordHash`/`googleId`),
  винесений у спільну константу `USER_SELECT` (спільна для `list()` і
  `GET /hurtky/:id/board`, щоб whitelist не розходився між місцями).

`GET /users/:id`

- Ті самі правила видимості, що й у списку вище: якщо запитувач не мав би
  права побачити цього користувача в списку — `404 Not Found` (не `403` —
  щоб не підтверджувати існування запису поза межами доступу, консистентно
  з `NotFoundException('Junak not found')` у наявному коді).
- JUNAK може запитати лише власний `id` (інакше 404).
- На відміну від списку, тут whitelist ширший — додатково `notes`, `phone`
  (контактні дані). Додано після фінального рев'ю 2026-08-29: без цього
  курінний/зв'язковий не мали жодного способу прочитати контакти, які їм
  щойно дозволили бачити — `?role=` у списку цього не покривав. Список
  (`GET /users`) навмисно лишається без цих полів — контакти показуються
  лише в детальному перегляді одного користувача.

### 4. Призначення виховників

`GET /vykhovnyk-assignments?hurtokId=`

- **ZVYAZKOVYI**: усі призначення куреня (опціонально звужені по
  `hurtokId`).
- **VYKHOVNYK**: лише власні призначення (query видає тільки записи де
  `vykhovnykId == actor.userId`; `hurtokId`-фільтр застосовується поверх).
- **KURINNYI**: усі призначення куреня, як і зв'язковий (лише перегляд —
  цей ендпоінт і так не має write-операцій для курінного; `POST`/`DELETE`
  на цьому контролері лишаються ZVYAZKOVYI-only). Додано після фінального
  рев'ю 2026-08-29: без цього курінний не мав жодного робочого шляху
  побачити, хто виховник якого гуртка.
- **JUNAK**: 403.

### 5. Дошка гуртка (агрегована view)

`GET /hurtky/:id/board`

- **VYKHOVNYK**: лише якщо призначений на цей гурток (інакше 404 — на
  відміну від `assertAssignedVykhovnyk` у `proby-progress.service.ts`,
  яка для того самого випадку кидає 403; тут свідомо 404, бо гурток —
  ресурс поза межами призначення виховника, консистентно із загальним
  404-правилом цього read-API, а не з тим конкретним хелпером).
- **ZVYAZKOVYI**: будь-який гурток свого куреня.
- **KURINNYI**, **JUNAK**: 403 як АКТОРИ — не можуть самі відкрити дошку
  гуртка (консистентно з наявним обмеженням `getProgressFor`: курінний
  бачить лише власний прогрес, не має адміністративного перегляду чужого).
- `junaky` у відповіді **включає курінного**, якщо він є членом цього
  гуртка (`role IN (JUNAK, KURINNYI)`, не лише `JUNAK`) — уточнено
  2026-08-29 разом із `2026-08-29-kurinniy-proby-tracking-design.md`:
  курінний завжди перебуває в конкретному гуртку, як і будь-який юнак, і
  саме через дошку його гуртка виховник бачить курінного та підтверджує
  йому точки — тим самим шляхом, що й для звичайного юнака.
- Повертає:
  ```
  {
    hurtok: { id, name, number },
    junaky: [
      {
        id, firstName, lastName, nickname, ...(whitelist як у списку користувачів),
        progress: [ { pointId, status, confirmedAt, point: {...} } ]
      }
    ]
  }
  ```
  `progress` — той самий формат, що повертає наявний
  `GET /junaky/:junakId/progress` (лише точки з існуючим `JunakProgress`
  записом; повний список точок програми фронтенд бере з
  `GET /proby-programs/current` і зіставляє сам).

### 6. Деталі запиту на затвердження

`GET /approval-requests/:id`

- Доступ: **ZVYAZKOVYI** свого куреня (та сама перевірка, що й у
  наявному `loadPendingRequestForKurin`, без обмеження статусом — можна
  переглянути вже вирішений запит).
- **KURINNYI**, **VYKHOVNYK**, **JUNAK**: 403.
- Доповнює наявний `GET /approval-requests` (список) — без змін до нього.

## Response shape

Без окремого DTO-шару — сервіси повертають Prisma-результати напряму з
`select`-whitelist, консистентно з рештою кодбази. Для `board` — вкладена
структура, зібрана в сервісі одним методом (не окремий модуль).

## Помилки

- `404 Not Found` — ресурс поза межами видимості ролі/тенанта/призначення
  (не розкриває існування чужих даних).
- `403 Forbidden` — ресурс у принципі існує в межах куреня, але роль не
  має права на цю дію (наприклад, курінний з `?role=VYKHOVNYK`).
- Обидва патерни вже використовуються в кодбазі — нових класів помилок не
  додається.

## Обмеження MVP (свідомі спрощення)

- **Без пагінації.** Курінь — десятки людей; повний список без пагінації
  прийнятний на цьому масштабі. Базові query-фільтри (`role`, `hurtokId`)
  замінюють потребу звужувати вибірку.
- **Каталог проб — лише поточна програма.** Перегляд інших/старих програм
  через це API недоступний (лише через admin bootstrapping). Якщо
  знадобиться порівняння програм для зв'язкового перед міграцією — окрема
  майбутня задача.
- **`board` не перевіряє належність гуртка до поточної програми проб
  куреня** — показує прогрес як є, той самий пробіл, що вже задокументовано
  для `GET /junaky/:junakId/progress` в основному дизайні (не масштабується
  на нове API, а успадковується від наявного).

## Тестування / перевірка

Для кожного нового ендпоінта — e2e-тест (supertest + наявні fixtures з
`test/utils/fixtures.ts`):

- Happy path для кожної ролі з доступом.
- Один forbidden/not-found кейс на роль без доступу.
- Tenant-isolation кейс: запит ресурсу з іншого куреня повертає 404.

Той самий підхід, що використовувався у всіх 19 задачах "Ядро + Проби".
