# Фронтенд "Ядро + Проби" — дизайн-документ

## Контекст і межі проєкту

Бекенд "Ядро + Проби" (див. `2026-08-28-yadro-proby-design.md`,
`2026-08-28-yadro-proby-backend.md`, `2026-08-29-read-api-design.md`) має
повний read+write API: 4 ролі (JUNAK, VYKHOVNYK, KURINNYI, ZVYAZKOVYI),
multi-tenant структура курінь→гурток, трекінг проб, воркфлоу запитів на
затвердження. Фронтенду досі немає — це перший клієнт для цього API.

Цей документ проєктує єдиний фронтенд-підпроєкт, що покриває весь наявний
API одним планом (свідомо не розбитий на "проби" і "адмінка" окремо — за
рішенням користувача).

### Явно поза межами цього підпроєкту

- Офлайн-режим / service worker з кешуванням (лише встановлюваність PWA —
  manifest + іконка).
- i18n-каркас (лише українська мова інтерфейсу).
- Екрани для майбутніх підсистем (AI-агенти, планування подій, реманент,
  соцстрічка).
- Кастомна брендована стилізація Пласту (типографіка/кольори/лого) —
  дефолтна shadcn-палітра для MVP.
- Push-нотифікації.
- Будь-які зміни в NestJS API — фронтенд споживає наявний API як є.

## Архітектура

**Стек:** Next.js 15 (App Router) + TypeScript, Tailwind + shadcn/ui,
TanStack Query, деплой на Vercel. Новий workspace `apps/web` у тому самому
npm-workspaces monorepo, поруч з `apps/api`.

**Next.js як BFF-проксі.** JWT зберігається в httpOnly cookie (недоступний
для клієнтського JS — захист від XSS; це свідомий компроміс: без цього
браузер не має способу додати `Authorization`-заголовок сам). Тому весь
трафік до NestJS API йде через один узагальнений Next.js Route Handler:

```
app/api/backend/[...path]/route.ts
```

Він приймає будь-який метод/шлях, читає JWT з httpOnly cookie на сервері,
додає `Authorization: Bearer <token>`, форвардить запит у NestJS
(`NEXT_PUBLIC_API_URL` або серверна env-змінна `API_URL`), повертає
відповідь (статус-код і тіло) як є. Браузер працює лише з Next.js
(той самий origin) — CORS на NestJS міняти не треба.

Клієнтський код (React-компоненти, TanStack Query hooks) звертається лише
до `/api/backend/...` — ніколи напряму до NestJS.

**Session-хендлер.** Окремий route handler `app/api/session/route.ts`:
читає httpOnly cookie на сервері, декодує JWT (без звернення до бекенду —
payload містить `sub`/`role`/`kurinId`, підпис не перевіряється тут, лише
парситься — авторизація й так перевіряється на кожному NestJS-запиті),
повертає `{ userId, role, kurinId } | null` клієнту. Клієнт використовує
це для рендеру ролі-залежної навігації, не для авторизації дій (та
відбувається на бекенді).

## Аутентифікація

**Email/пароль:**
1. Форма на `/login` (email, пароль) → `POST /api/auth/login` (Next.js)
2. Route handler форвардить у `POST /auth/login` (NestJS) з `{ email,
   password }`
3. NestJS повертає `{ accessToken }`
4. Route handler ставить `accessToken` у httpOnly cookie (`Set-Cookie`,
   `httpOnly`, `secure` в проді, `sameSite=lax`, `maxAge` = 1 день), відповідає
   клієнту success
5. Клієнт редіректить на `/`

**Google SSO:**
1. Кнопка "Увійти через Google" на `/login` — Google Identity Services
   (клієнтський JS SDK), отримує `idToken`
2. `POST /api/auth/google` (Next.js) з `{ idToken }` → форвардить у
   `POST /auth/google` (NestJS)
3. Той самий httpOnly-cookie флоу, що й вище

**Сесія:** токен живе 1 день (`JWT_EXPIRES_IN` на бекенді), без
refresh-механізму. Проксі-хендлер: якщо NestJS повертає `401` на будь-який
запит — клієнт глобально редіректить на `/login` (обробляється в
TanStack Query `onError`/`QueryClient` рівні, не в кожному хуку окремо).

**Logout:** `POST /api/auth/logout` (Next.js-only route, немає бекенд-
відповідника) — просто очищує cookie, редірект на `/login`.

## Роутинг і навігація

`middleware.ts` перевіряє наявність cookie на кожному запиті (крім
`/login` і статики) — немає cookie → редірект на `/login`. Роль-специфічна
видимість — на рівні UI (навігація, приховані посилання), фактична
авторизація дій — суто на бекенді (фронтенд не дублює бізнес-правила
видимості, лише ховає недоступні пункти меню й акуратно показує
403/404-відповіді).

Навігація в шапці — пункти меню залежно від ролі, отриманої з
`/api/session`.

## Екрани

### Спільне

- `/login` — форма email/пароль + кнопка Google. Публічний маршрут.

### Юнак

- `/proby` (домашній екран юнака, `/` редіректить сюди для цієї ролі) —
  чекліст проби: ступені → категорії → точки з позначками здано/не здано.
  Джерела даних: `GET /proby-programs/current` (структура дерева) +
  `GET /junaky/:userId/progress` (свій прогрес, `userId` з сесії) —
  зведені на клієнті: кожна точка з дерева шукає відповідний запис
  прогресу за `pointId`, якщо немає — вважається "не здано". Read-only,
  жодних мутацій.

### Виховник

- `/hurtky` (домашній екран виховника) — список гуртків, до яких
  призначений (`GET /vykhovnyk-assignments`, з даними гуртків із
  `GET /hurtky` для назви/номера)
- `/hurtky/[id]` — дошка гуртка (`GET /hurtky/:id/board`): список юнаків
  з прогресом кожного по точках. Кнопки "підтвердити"/"зняти" на кожній
  точці кожного юнака — `POST /junaky/:id/progress/:pointId/confirm` /
  `.../unconfirm`. Після мутації — інвалідація query board цього гуртка.

### Курінний

Усе, що бачить виховник (без обмеження призначенням — курінний не має
`/hurtky/:id/board`, бо бекенд забороняє курінному прогрес проб; курінний
не отримує посилань на дошку гуртка в навігації), **плюс**:

- `/users?role=JUNAK` (домашній екран курінного) — список юнаків куреня
  (`GET /users?role=JUNAK`), з фільтром по гуртку. Кнопка "додати юнака"
  веде на форму, що при сабміті створює `ApprovalRequest` типу
  `CREATE_JUNAK` (`POST /approval-requests`), не самого юнака напряму —
  курінний не може створювати юнаків без затвердження.
- `/users/[id]` — картка юнака: перегляд усіх полів; форма редагування
  нотаток/телефону (`PATCH /users/:id/contact-info`, застосовується
  одразу); окрема форма для ПІБ/дати народження/email/гуртка — сабміт
  створює `ApprovalRequest` (`CHANGE_FULL_NAME` / `CHANGE_BIRTH_DATE` /
  `CHANGE_EMAIL` / `CHANGE_HURTOK`) замість прямого `PATCH`, з поясненням
  в UI "очікує підтвердження зв'язкового".
- `/users?role=VYKHOVNYK` та `/users?role=ZVYAZKOVYI` — перегляд контактів
  виховників і зв'язкового (`GET /users/:id` віддає `phone`/`notes` на
  деталях). Без кнопок редагування — курінний лише переглядає.
- `/vykhovnyk-assignments` — перегляд (не керування) списку "хто виховник
  якого гуртка" (`GET /vykhovnyk-assignments`, курінному тепер дозволено).
- `/proby-programs/current` — перегляд каталогу проб куреня, read-only,
  довідково (щоб бачити повний опис точок при редагуванні юнака).

### Зв'язковий

Усе, що бачить курінний (з правом редагування там, де курінний його не
має), **плюс**:

- `/hurtky/new` — форма створення гуртка (`POST /hurtky`)
- `/vykhovnyk-assignments` — тут уже з керуванням: призначити виховника на
  гурток (`POST /vykhovnyk-assignments`), зняти призначення
  (`DELETE /vykhovnyk-assignments/:id`)
- `/users/new` — форма створення юнака/виховника/курінного напряму
  (`POST /users`) — на відміну від курінного, зв'язковому не потрібен
  approval-request
- `/users/[id]` — зміна ключових полів юнака (ПІБ/дата народження/email/
  гурток) для зв'язкового йде тим самим шляхом, що й для курінного —
  через approval-request. Наявний API не має окремого прямого write-
  ендпоінта для ключових полів юнака (лише `PATCH /users/:id/contact-info`
  для другорядних полів і сам approval-request флоу), а розширення API —
  поза межами цього фронтенд-підпроєкту. Зв'язковий після створення
  запиту одразу переходить на `/approval-requests/[id]` і сам собі
  затверджує — незручно за один крок, але коректно за наявним API.
- `/approval-requests` (домашній екран зв'язкового) — черга запитів
  (`GET /approval-requests`, з фільтром по статусу), кожен рядок — перехід
  на деталі
- `/approval-requests/[id]` — деталі запиту (`GET /approval-requests/:id`)
  з кнопками "затвердити"/"відхилити" (`POST .../approve` /
  `.../reject`), активними лише для запитів у статусі PENDING
- `/kurin` — налаштування куреня: перегляд (`GET /kurins/me`), зміна
  програми проб (`PATCH /kurins/:id/proby-program`)

## Дані та мутації

TanStack Query на клієнті. Кожен ресурс — свій набір хуків у
`lib/queries/<resource>.ts` (напр. `useHurtokBoard(hurtokId)`,
`useUsers(filters)`, `useApprovalRequests(status)`). Query keys включають
усі параметри фільтрації, щоб кеш коректно розділявся.

Мутації — `useMutation` з `queryClient.invalidateQueries` на пов'язані
ключі:
- confirm/unconfirm точки → інвалідує board цього гуртка (і, якщо потрібно
  показати оновлений прогрес деінде, прогрес відповідного юнака)
- approve/reject запиту → інвалідує список запитів + деталі цього запиту +
  (якщо запит змінював юнака) картку юнака
- create/update юнака чи призначення → інвалідує відповідний список

## Обробка помилок

Проксі-хендлер прозоро передає статус-код і тіло відповіді NestJS без
трансформації.

- **401** — глобальний редірект на `/login` (протухлий/відсутній токен).
  Обробляється централізовано на рівні `QueryClient`
  (`queryCache.onError`), не в кожному хуку.
- **403 / 404** — компонент показує нейтральне повідомлення ("Немає
  доступу" / "Не знайдено") без деталей про причину — сервер навмисно не
  розрізняє "не існує" від "недоступно" там, де це важливо для
  тенант-ізоляції, і фронтенд цього не намагається вгадати.
- **400** (помилка валідації) — тіло відповіді NestJS
  (`ValidationPipe`) містить масив повідомлень по полях; форма показує їх
  біля відповідних інпутів.
- Мережеві помилки / 5xx — загальний тост "Щось пішло не так, спробуйте
  ще раз".

## Тестування

Playwright e2e, що запускається проти реального Next.js + реального
NestJS + тестової БД (`DATABASE_URL_TEST`, той самий підхід, що й бекенд-
тести) — не проти мокнутого API. Ключові сценарії, що мають бути покриті:

1. Логін email/пароль → потрапляння на домашній екран своєї ролі
2. Виховник підтверджує точку на дошці гуртка → бачить оновлений статус
3. Курінний редагує нотатки юнака напряму (без approval) і змінює ПІБ
   (створюється approval-request, юнак ще не змінений)
4. Зв'язковий бачить запит у черзі, затверджує його → дані юнака
   змінились
5. Зв'язковий створює нового юнака, призначає виховника на гурток
6. 401 (протухлий токен) → редірект на `/login`
7. Роль без доступу до екрана (напр. юнак відкриває `/users`) → показ
   403-стану, не крах додатку

Компонентні/юніт-тести для UI-логіки — точково, де є нетривіальна логіка
(напр. зведення дерева проб з прогресом), не для кожного компонента.

## Розгортання

Vercel для `apps/web` (Next.js) — окремо від бекенду на Hostinger VPS.
Змінні середовища: `API_URL` (серверна, для проксі-хендлера, вказує на
NestJS), публічний `NEXT_PUBLIC_GOOGLE_CLIENT_ID` (для Google Identity
Services SDK на клієнті).

## Обмеження MVP (свідомі спрощення)

- **Зв'язковий редагує ключові поля юнака через той самий
  approval-request-флоу, що й курінний**, і сам собі затверджує запит —
  бекенд не має окремого "прямого" write-шляху для зв'язкового, а
  розширення API — поза межами цього фронтенд-підпроєкту. Незручно, але
  функціонально коректно.
- **Немає офлайн-режиму** — без інтернету застосунок не працює.
- **Немає пагінації в списках** (успадковано з backend read-API — курінь
  на масштабі десятків людей, повний список прийнятний).
- **Без кастомного брендингу** — дефолтна shadcn-палітра.
